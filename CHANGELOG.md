# Changelog

## Unreleased

- CI: the `postgres-integration` job now runs Postgres 16 with TLS on (#209). A service container cannot mount a certificate, so the server is started by a step with a throwaway self-signed certificate; the job sets `APP_TEST_POSTGRES_REQUIRE_TLS=1`, which makes `test_startup_tls_check` fail instead of skipping its success path when the server has no TLS. This covers the `pg_stat_ssl` start-up check (#139) and `sslmode=require` on the happy path; `verify-full` against a real certificate authority and a transaction pooler remain unproven.
- Telemetry on the reference deployment (#156, ADR 0008 decision 12), repo side only. `OPERATIONS.md` documents the path (instances to the private-service Collector to the backend), why one Collector replica needs no trace-ID load balancing, the secret-file upload, the shared-private-network caveat and the leak-scan procedure for staging output; `tests/unit/test_render_blueprint.py` now pins `APP_OTEL_ENABLED=true`, a sample ratio of 1.0, an endpoint to the environment's own Collector, the pinned Collector release, the shipped config as a secret file and a Collector with no application secret. Not done (the owner deferred a real Render deploy): a live staging trace, logs and metrics in a backend, the shipped alert rules loading there, and the leak scan of staging telemetry. The Collector image is still pinned by tag, not digest.
- Runbooks (#154). `OPERATIONS.md` gains a "Runbooks" section: deploy, rollback (redeploy the previous digest, when that is safe, never hand-editing tables), migration failure, roles (create and rotate), rotation of each secret with a maximum age and `APP_IDENTITY_HASH_KEY` as a maintenance operation, backups and restore to a new database (with an RTO/RPO template, not recorded values), capacity (table-size query and threshold) and platform facts. `tests/unit/test_runbooks.py` checks the headings, that the CLI commands exist and that no secret appears; the existing test already ties every alert to a runbook heading. Render facts are assumptions and no procedure was rehearsed on a real deployment; the restore drill and the recorded RTO/RPO remain for the release gate.
- Deploy pipeline (#151, ADR 0008 decision 6, steps 5 to 7). New `.github/workflows/deploy.yml`: after a successful `image-publish` run on `main`, staging is deployed by digest (green `ci` required, attestation verified against the pinned signer, per-service deploy hooks, smoke test); a `v*` tag promotes the digest recorded by the tagged commit's `main` build run, never a tag and never a rebuild, in the `production` Environment, after the tag-on-`main`, `pyproject.toml`/`CHANGELOG.md` and passing-staging checks, then publishes the GitHub Release. `image-publish.yml` now keeps the digest in an `image-digest` artifact. `scripts/deploy_tools.py` holds the decisions and the hook calls (digest-only images, hooks never printed). Not done: a real staging deploy end to end and a recorded failing-attestation run (the owner deferred a real Render deploy), and confirmation that each service reports the new digest (no Render API is used; a fixed settle wait plus the smoke test stand in). Needs Environment secrets `DEPLOY_HOOKS` and `SMOKE_TEST_TOKEN` and variable `SMOKE_TEST_URL`.
- Fix: trusted-proxy client-IP resolution now accepts `X-Forwarded-For` entries of the form `ip:port`, `[v6]` and `[v6]:port` (#208). They used to end the walk at the proxy's own address, so all clients shared one rate-limit bucket. A valid port is stripped; any other unparseable entry still ends the walk and nothing to its left is believed.
- Fix: `/health/ready` now fails (503) with `APP_LIMITS_BACKEND=postgres` when the guard tables (`neuron_run_leases`, `neuron_token_ledger`, `neuron_token_settlements`, `neuron_rate_buckets`) are missing, for example when `setup` was not run (#207). The existing readiness ping also runs one `to_regclass` check over `migrations.GUARD_TABLES`, derived from the app-role grant table so it follows new guard tables; it keeps the ping timeout, and a failure logs `guard_tables_missing` with the table names only. Nothing extra runs with the in-memory limits backend.
- Fix start-up crash when `APP_POSTGRES_POOL_MAX_SIZE` is 1 to 3 (#205). The pool's `min_size` is now capped at the configured maximum instead of defaulting to 4.
- Fix: `psycopg_pool` no longer leaks the database password into logs (#204). When a connection failed, libpq errors that echo the connection string (for example a malformed URI) were logged verbatim by the `psycopg.pool` logger. `build_persistence` now installs a logging filter on the `psycopg` and `psycopg.pool` loggers that redacts the configured DSN and its password. New `tests/unit/test_dsn_redaction.py` captures all log output through a failed connect, and the `setup` CLI output, with a distinctive password. The migration path (`persistence.cli setup`) uses a direct connection, not the pool, and already printed only the exception class name.

- Render Blueprint for staging and production (#150, ADR 0008 decisions 1, 10 and 15). New `render.yaml` defines both environments: an image-backed web service per environment from `ghcr.io/md-nisar/neuron` (production two instances, staging one; health check `/health/ready`; pre-deploy `python -m neuron_agent.persistence.cli setup`; `maxShutdownDelaySeconds: 180`), a Render Postgres database with an empty `ipAllowList`, a daily `prune` cron job, a Collector private service, and non-secret settings in environment groups split per role and environment. Every secret is `sync: false` on its service (Render does not allow it in a group); the runtime DSN is the app role's, never `fromDatabase`. `tests/unit/test_render_blueprint.py` checks the file and that its values pass `Settings` validation. `OPERATIONS.md` "Deployment" is rewritten around it (role creation, connection budget, who can read the secrets). Not done: Render's own validation and a staging deploy from the file. The shutdown delay is 180, not the 150 first proposed, because 150 has no margin with OpenTelemetry on (ADR 0008 decision 1 is amended).
- **Breaking: database start-up checks (#139, ADR 0008 decisions 15 and 16).** In staging and production the pool's first connection must pass, in this order, a TLS check (`pg_stat_ssl` shows `ssl = true` for the process's own backend), in production the existing role check, and an identity key check (this process's `APP_IDENTITY_HASH_KEY` check value against the one `setup` recorded in `neuron_meta`). Any failure closes the pool, logs `database_startup_check_failed` once with a stable `error_code` (`tls_required`, `role_not_app_user`, `role_too_privileged`, `identity_key_mismatch`, `identity_key_unrecorded`, `database_check_failed`; never a DSN, password or key) and stops start-up, as `AppRoleError` already did; the prune CLI runs the same checks and exits 1 printing the code. Migration 12 (`identity_status_function`, expand-only) adds `neuron_identity_status(text)`, a `SECURITY DEFINER` function that answers `match`, `mismatch` or `unset` for a candidate check value, so the app role still cannot read `neuron_meta`; `setup` grants `EXECUTE` on it to the app role only. Breaks a deployment whose database connection is not TLS, or whose `setup` has not run with the current key since this release (run `setup` before the new image starts). `AppRoleError` is now a `StartupCheckError` carrying a `code`; development and test run none of the checks.
- **Breaking: production settings validation (#138, ADR 0008 decision 9).** `Settings` refuses unsafe staging and production configuration at start-up; development and test are unchanged. Each rule below breaks an existing staging or production deployment that relies on the old default, and every error names the setting, never its value (`hide_input_in_errors` is on, so a DSN or key is not echoed either). (1) **Breaking:** `APP_CHECKPOINTER=auto` and `APP_LIMITS_BACKEND=auto` are refused in staging and production (ADR 0005 decision 1 amended): set `postgres`, or `none` for a deliberately stateless deployment (logged at warning level at start-up as `stateless_deployment`); a deployment that relied on `auto` resolving to `none` must now say `none`. (2) **Breaking:** `APP_LIMITS_BACKEND=memory` is refused in production. (3) **Breaking:** an empty `APP_ALLOWED_HOSTS` is refused. (4) **Breaking:** an unset `APP_TRUSTED_PROXIES` is refused (an explicit `[]` is accepted, told apart with `model_fields_set`), as is any catch-all range (`0.0.0.0/0`, `::/0`). (5) **Breaking:** `APP_RATE_LIMIT_ENABLED=false` is refused. (6) `APP_CHECKPOINTER_SETUP_ON_STARTUP=true` stays refused (already enforced since #143; now covered by the production profile tests). (7) **Breaking:** a runtime or migration Postgres DSN needs an explicit `sslmode` in the DSN (parsed with psycopg's `conninfo_to_dict`, so URI-query and keyword forms both work; a DSN with no `sslmode` is refused because libpq would default to `prefer`): `verify-full` in production; staging also accepts `require` and `verify-ca`, the documented free-plan exception of ADR 0008 decision 17. `PGSSLMODE` in the environment does not count. (8) **Breaking:** `APP_EXPOSE_API_DOCS=true` is refused in production. (9) **Breaking:** in staging and production the JWKS URL's host must not be `localhost`, or a loopback, link-local or private address literal (names are not resolved). (10) **Breaking:** in production `APP_LANGSMITH_CONTENT_APPROVED=true` needs the new `APP_LANGSMITH_CONTENT_APPROVAL_RECORD`, naming the approval record. Review follow-up: the JWKS host check now reuses `validate_safe_url` (inet_aton spellings such as `2130706433` and `0x7f.1`, NAT64, 6to4, shared space, multicast, reserved and unspecified addresses are refused); staging and production refuse `APP_ALLOWED_HOSTS` entries `*` and `*.<tld>`; trusted proxy ranges broader than /8 (IPv4) or /16 (IPv6) are refused, not only `/0`; the approval record is logged once at start-up as `langsmith_content_capture_approved`. At start-up the effective limits (rate, burst, concurrency, token budget, timeouts and the limits backend) are logged once as `effective_limits`. (11) **Breaking:** `APP_HSTS_MAX_AGE_SECONDS=0` is refused in production (ADR 0008 open question 13 resolved: the production API is TLS-only, so HSTS is always safe to send); staging may leave it off. Deliberately not a rule: refusing `APP_AUTH_REQUIRE_TYP=false` (open question 2 resolved: no identity provider is chosen, and refusing would force `at+jwt` on providers that do not issue it; the audience, issuer and scope checks already apply, so `APP_AUTH_REQUIRE_TYP=true` stays a recommended hardening to set once the provider is known to issue RFC 9068 tokens).
- Shared request rate limiting in Postgres (#148, ADR 0004, ADR 0008 decision 8). New `persistence/rate_limiter.py` (`PostgresRateLimiter`) behind `APP_LIMITS_BACKEND=postgres`: an `UNLOGGED` token-bucket table `neuron_rate_buckets` (migrations 10 and 11, expand-only: the table and a concurrent index on `refilled_at`), one atomic `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` per rate-limited request with database-clock timestamps, so a burst split across replicas is limited to `APP_RATE_LIMIT_BURST` in total. Keys keep the `principal:` and `ip:` namespaces; the `ip:` key is now an HMAC of the client address (IPv6 as its /64) under a key derived from `APP_IDENTITY_HASH_KEY` with HKDF and its own label (the plain address remains the key with the in-memory limiter when that key is unset), so no raw IP is stored; it is pseudonymous and the table is personal data (`SECURITY.md`). Idle buckets are deleted as the limiter writes and by the retention job (`prune` reports `idle_rate_buckets`). A bounded in-memory IP limiter runs in front of the shared one for `AUTH_MODE=none` requests and failed authentication, so a flood does not cost a database write per request. A database error is `503 persistence_error`. Because the three guards are now all Postgres-backed, the real app starts with `APP_LIMITS_BACKEND=postgres` (the remaining `NotImplementedError` is gone); it requires `APP_IDENTITY_HASH_KEY` when rate limiting is enabled. `security/auth.py` no longer imports `api/main.py`: the app injects the limiters, verifier and client-IP function through `app.state.request_security` (a test pins that no module in `security/` imports `api/`). The `UNLOGGED` table is empty after a crash, unclean shutdown, failover or point-in-time restore, which grants every caller a fresh burst (`OPERATIONS.md` "Rate Limiting"). The `setup` grant phase gives the app role DML on the new table. Hardening: at most `APP_POSTGRES_POOL_MAX_SIZE // 2` limiter transactions per process (0.5 s slot wait, 500 ms `lock_timeout`, then `503`), table `fillfactor = 70` with a tighter autovacuum, a 5 s clock-damage reset and `tokens >= 0` CHECK, and a batched retention delete.
- Durable per-user token budget in Postgres (#147, ADR 0008 decision 8). New `persistence/token_budget.py` (`PostgresTokenBudget`) behind `APP_LIMITS_BACKEND=postgres`: a logged ledger `neuron_token_ledger (owner_key, minute, tokens)` (migrations 6 and 7, expand-only: the table with a `tokens >= 0` CHECK and its primary key, and a concurrent index on `minute`; the #144 grant phase gives the app role `SELECT`, `INSERT`, `UPDATE`, `DELETE` on it and `SELECT`, `INSERT`, `DELETE` on `neuron_token_settlements`) shared by every replica and surviving restarts. `TokenBudget` changes from `check`/`charge` to `reserve`/`settle` (both implementations): admission reserves `APP_MAX_OUTPUT_TOKENS` plus a prompt estimate (UTF-8 bytes / 3), capped at the budget, and refuses with `429 quota_exceeded` and `Retry-After` when the window plus the reservation exceeds it; every run settles to the real usage in the existing `finally` on every path (success, error, timeout, cancellation, disconnect), to the whole reservation when the run reports no usage (previously nothing was charged; see the follow-ups below), and a run that never started (or whose thread resolution or claim failed after admission) gives its reservation back. In-memory admission now also counts the reservation, so a budget smaller than one `APP_MAX_OUTPUT_TOKENS` + prompt reservation admits one run from an empty window instead of ever refusing. Postgres admission is one `READ COMMITTED` transaction serialised per owner by `pg_advisory_xact_lock`, so concurrent admissions cannot exceed the budget; the charge is one `INSERT ... ON CONFLICT DO UPDATE SET tokens = <table>.tokens + EXCLUDED.tokens`; every timestamp is the database's (`clock_timestamp()`); a minute counts until its end plus `APP_USER_TOKEN_BUDGET_WINDOW_SECONDS` has passed (one-minute granularity: up to 60 s longer than the window, never shorter). Any database error at admission is `503 persistence_error` before the model is called (`lock_timeout` 2 s, `statement_timeout` 5 s). A settlement the ledger refuses never blocks the answer: it is logged (`token_budget_settle_failed`), counted (new metric `neuron.token_budget.settle_failures`), kept in the process, and retried at that owner's next admission on the same replica, which fails closed until it succeeds; a crash loses the retry and the reservation stays counted. The retention job (`make prune-threads`) deletes ledger minutes outside the window (Postgres backend only; a failure is logged and never stops thread pruning). `APP_LIMITS_BACKEND=postgres` still stops the real app at start-up, now with the accurate `NotImplementedError` that the request rate limiter has no Postgres version (#148). The Postgres tests (`tests/integration/test_postgres_token_budget.py`, marker `postgres`) include two Uvicorn processes: usage charged on one is refused on the other, and the same scenario passes with the in-memory budget. `ARCHITECTURE.md`, `OPERATIONS.md`, `SECURITY.md`, ADR 0004, 0006 and 0008 no longer say a shared budget is out of scope. Review follow-ups: settlement is idempotent (migrations 8 and 9, `neuron_token_settlements`: the reservation id is recorded in the same transaction as the ledger change, so a retry after an ambiguous commit cannot subtract twice); a run that reports no usage (cancelled, timed out, or a provider that omits usage) now keeps its whole reservation instead of the prompt estimate, and only a run that never reached the model gives it back; the budget is documented as admission-time with settlement afterwards (a run can overshoot by its real cost); any non-psycopg failure in the budget is `PersistenceError` (503) rather than a 500; the retry lock is per owner; a per-owner gate (`2 x APP_MAX_CONCURRENT_RUNS_PER_USER`) bounds the pool connections one owner's admissions hold; `APP_USER_TOKEN_BUDGET_WINDOW_SECONDS` below `APP_RUN_TIMEOUT_SECONDS` + 15 is refused with the Postgres backend; the prune job keeps at least an hour of ledger. Protocol change: `TokenBudget.check`/`charge` became `reserve`/`settle` for both backends, and in-memory admission is now stricter (window usage plus the reservation must fit, instead of only usage below the budget); empty in-memory owner entries are dropped.
- Least-privilege database roles (#144, ADR 0008 decisions 15 and 16). `setup` run as `neuron_migrator` now grants the app role (`APP_POSTGRES_APP_ROLE`, default `neuron_app`) DML only, on every run: `SELECT, INSERT, UPDATE, DELETE` on the checkpoint tables, `SELECT, INSERT, DELETE` on `neuron_run_leases`, nothing on the new `neuron_meta` table (migration 5, expand-only) or the bookkeeping tables, tightened in the transaction that creates each table, plus default privileges for tables created later; no `CREATE`, `DROP`, `TRUNCATE` or ownership. `setup` stores an HMAC check value of `APP_IDENTITY_HASH_KEY` in `neuron_meta` once and fails on a different key unless `--rotate-identity-key` is passed (errors never echo the key or value). With one role, or a missing app role, the grants are skipped with a `app_role_grants_skipped` log line (staging only, ADR 0008 decision 17); `APP_ENV=production` fails instead. `OPERATIONS.md` has the role-creation SQL; `SECURITY.md` records the guard tables, the role split and that `setup` and `prune` are operator-only CLIs. In production, settings refuse equal runtime and migration DSN users, the web process refuses to open its pool unless it runs as the app role and that role is not superuser, `BYPASSRLS`, a member of the schema owner or able to `CREATE`, and `setup` verifies the app role and the privilege matrix. Identity key first write and rotation emit audit events; `setup` rejects `--older-than-days`; `pg_`-prefixed role names are refused. Not yet: the run-time identity key comparison (decision 16), and `CREATE ROLE` on Render is unproven (open question 20).
- Alerts for availability, readiness, the database and denied tools; configs validated in CI (#155, ADR 0008). Two unlabelled observable gauges: `neuron.service.ready` (readiness evaluated by a lifespan task every 15s, 1 or 0, independent of probes; it reports nothing while draining or when the last evaluation is over 60s old, so a terminating or hung instance goes quiet) and `neuron.db.pool.waiting` (`requests_waiting` from the psycopg pool's `get_stats()`, reported while a pool is open); names are in `observability/semconv.py`, no label was added and none carries user data. Seven new example alerts in `prometheus-alerts.yaml` (labelled `signal`): `NeuronNoMetrics` (`absent()` on the readiness gauge; there is no per-instance `up` because instances push over OTLP, and the Collector expires a series after 5m, so with `for: 5m` it fires no sooner than 10m after the last push), `NeuronInstanceNotReady` and `NeuronPostgresPoolSaturated` (5m, page), `NeuronRunLeasesExpired` (`max(neuron_run_leases_expired) > 0` for 5m, ticket; the maximum across replicas because each reports the table-wide count), `NeuronThreadBusyAnomaly` and `NeuronTooManyConcurrentRunsAnomaly` (above 5% of `/v1` requests and 0.05/s for 15m, ticket, from `neuron_agent_errors_total`) and `NeuronDeniedToolCallsSpike` (more than 10 `insufficient_scope`/`unknown_tool` blocks in 10m, ticket). Thresholds are provisional. Each has a runbook in `OPERATIONS.md`, and `SECURITY.md` no longer says that no example alert covers denied tool calls. New `scripts/validate_observability.py` downloads `promtool` 3.5.0 and `otelcol-contrib` 0.120.0 (pinned by URL and SHA-256, verified before extraction), runs `promtool check rules` and `otelcol-contrib validate`, and with `reject-broken` proves that each exits non-zero on a broken fixture; the new `observability-config` job of `ci` runs both with read-only permissions and no secrets. Not done: a Linux arm64 or Windows pin for the validators.
- Shared run leases in Postgres (#146, ADR 0008 decision 8). New `persistence/run_guard.py` (`PostgresRunGuard`) behind `APP_LIMITS_BACKEND=postgres`: each run holds a row in the new `neuron_run_leases` table (migrations 2 to 4, expand-only: the table with a `kind` CHECK and a unique `thread_id`, and concurrent indexes on `owner_key` and `expires_at`; needs Postgres 13 for `gen_random_uuid()`; after #144 splits roles the app role needs `SELECT`, `INSERT`, `DELETE` on `neuron_run_leases`, recorded as a #144 prerequisite with no grants added here), so `409 thread_busy` and `APP_MAX_CONCURRENT_RUNS_PER_USER` (`429 too_many_concurrent_runs`) hold across replicas. A claim is one `READ COMMITTED` transaction, serialised per owner by `pg_advisory_xact_lock` (transaction-level only; no new session lock), with `lock_timeout` 2 s and `statement_timeout` 5 s; every timestamp is the database's, `expires_at = clock_timestamp() + APP_RUN_TIMEOUT_SECONDS + 15 s` (`clock_timestamp()`, not the transaction-start `now()`, so a wait for the owner lock does not shorten the lease), no heartbeat or fencing; release deletes the row, is idempotent, shielded and never raises (a failed release is logged and expiry covers it); a unique violation on `thread_id` is `thread_busy`, never a 500; the lease id is generated by the app, so a claim cancelled after its commit deletes its own row in a shielded cleanup. Any other guard failure (database down, owner lock held past the timeout, pool exhausted) fails closed: `503 persistence_error` and no model call. `RunGuard` gains `hold_thread`; `DELETE /v1/threads/{id}` and the bulk erase hold a lease on each thread while it is deleted (previously they checked this process's active threads only), and the bulk erase counts a thread whose run started after the listing as `skipped_busy_count`. The retention job (`make prune-threads`) deletes expired leases after thread pruning, only with the Postgres backend, and a lease-table failure is logged without aborting thread pruning; the bulk erase counts in `skipped_busy_count` only owned threads it skipped (not every active lease of the owner) and audits a part-way failure with the count so far; and a new gauge `neuron.run_leases.expired` (every replica samples the table-wide count every 30 s) is ready for an alert (#155). `APP_MAX_CONCURRENT_STREAMS` stays per process. New two-process harness `tests/integration/pg_harness.py` (two Uvicorn servers on one database) for #147 and #148, with the tests in `tests/integration/test_postgres_run_guard.py` (marker `postgres`). Still not enabled: the request rate limiter and token budget have no Postgres version, so the app stops at start-up with `APP_LIMITS_BACKEND=postgres` (`NotImplementedError`) until #147 and #148; `auto` still resolves to `memory`; staging and production rules for the setting are #138. ADR 0005 (decision 5, Consequences), ADR 0006 (Non-goals), `OPERATIONS.md` (Scaling) and `ARCHITECTURE.md` say the guards are shared with the Postgres backend.
- Graceful shutdown for invoke (#136, ADR 0008 decision 4). `AgentService.begin_drain()` (idempotent, never raises, logs `service_draining` once with `in_flight_runs`) is called by `neuron-api`'s new `uvicorn.Server` subclass from `handle_exit` before Uvicorn's own handling: `/health/ready` returns `503` at once, and after the new `APP_SHUTDOWN_DRAIN_SECONDS` (default `5`, `0`-`60`) `AgentService.prepare` raises `ShuttingDownError`, which `invoke` and `stream` map to `503 service_shutting_down` with `Retry-After: 1`. On SIGTERM the Server subclass also holds Uvicorn's own stop for the drain delay (so the listener stays open while the load balancer converges) and makes a clean shutdown exit `0` instead of re-raising SIGTERM (status 143). Uvicorn's graceful timeout is unchanged (`APP_RUN_TIMEOUT_SECONDS + 10`) but now starts after the delay, so the platform grace must exceed `APP_SHUTDOWN_DRAIN_SECONDS + APP_RUN_TIMEOUT_SECONDS + 10` (`OPERATIONS.md`, "Shutdown"). `main()` builds the server through `build_server()` and no longer calls `uvicorn.run`. Open streams therefore end after the drain delay, not at SIGTERM. With `--reload` the delay is 0. Not done: flushing pending charges for runs that a SIGKILL ends (no Postgres guards yet).
- Versioned schema migrations as a deploy step (#143, ADR 0008 decision 7). `persistence/migrations.py` holds an ordered list of neuron migrations recorded in a `neuron_migrations` table and applied by `python -m neuron_agent.persistence.cli setup` after LangGraph's `setup()`; the owner index is migration 1, built `CONCURRENTLY` outside a transaction, and an `INVALID` leftover is dropped and rebuilt instead of skipped. `setup` runs on one direct connection that holds a session advisory lock for the whole run (concurrent runs serialise; the one session lock in neuron, ADR 0008 open question 19) and sets a 5 second `lock_timeout` for transactional DDL (concurrent index builds get 10 minutes, since they also wait on older transactions), and it exits non-zero on any failure, printing only the error class and SQLSTATE, never a DSN or password. New `APP_POSTGRES_MIGRATION_DSN` (`SecretStr`): required by `setup` in staging and production with no fallback to the runtime DSN, development falls back; only `persistence.cli` reads it, which a test enforces. `setup` with no database configured now exits non-zero (it used to do nothing). `APP_CHECKPOINTER_SETUP_ON_STARTUP=true` is now refused in staging and production, and elsewhere uses the same migrations. A test enforces the expand/contract rule on every migration. New `docs/rollback-test-checkpoint-postgres.md` for `langgraph-checkpoint-postgres` bumps, referenced from `SECURITY.md`. Postgres tests are in `tests/integration/test_postgres_migrations.py` (marker `postgres`).
- Image CI: build, scan and attest (#140, ADR 0008 decision 6, steps 2-4). New `image-publish` workflow, on pushes to `main` only: buildx build with `provenance: mode=max` and an SBOM, push to `ghcr.io/md-nisar/neuron:sha-<commit>`, a Trivy scan of the pushed digest that fails on fixable HIGH or CRITICAL findings (the vulnerability database is downloaded at run time, caching is off and a failed update fails the scan), then an `actions/attest` SLSA provenance attestation pushed to the registry. Permissions are per job; only the `attest` job has `id-token: write` and `attestations: write`, and no other workflow may. Ignores live in `.trivyignore.yaml` (reason and a date at most 90 days out, checked by a test). Every new action is pinned by commit SHA. Pull requests are still built, without a push, by `docker-build`. Trivy is chosen here for its dated ignore file; ADR 0008 open question 9 still lists Grype as proposed. GHCR visibility is left at the default (open question 14 is undecided). `SECURITY.md`, `OPERATIONS.md` ("Published image and attestation", with the `gh attestation verify` command) and `docs/AI_CODE_VERIFICATION.md` describe it. Not yet confirmed: the first run on `main` (push, scan, attest, verify).
- Server entrypoint (#135, ADR 0008 decision 3). The image now runs `neuron-api`, which builds Uvicorn's configuration from `Settings`: new `APP_HOST` (default `127.0.0.1`) and `APP_PORT` (default `8000`; `PORT` also accepted and wins, for Render), `timeout_graceful_shutdown = APP_RUN_TIMEOUT_SECONDS + 10`, one process, and Uvicorn's proxy-header rewriting off, so `_client_ip` is the only parser of `X-Forwarded-For` (open question 5, decided by the owner on 2026-10-20). `main()` exits non-zero on a non-loopback `APP_HOST` unless `APP_ENV` was set explicitly; the image sets `APP_HOST=0.0.0.0` and `APP_PORT=8000`, so an image started without `APP_ENV` no longer serves unauthenticated, and `docker-compose.yml` sets `APP_ENV=development`. The image `HEALTHCHECK` uses the configured port. `HOST`/`PORT` are no longer read with `os.getenv`; a test fails on any environment access under `src/` outside `config/settings.py`, `langsmith_governance.py` and `telemetry.py` (both listed in `AGENTS.md`). `reload` is on only for `development` on a loopback host. ADR 0004 and `OPERATIONS.md` no longer tell operators to set `--forwarded-allow-ips`. `make api` still runs `uvicorn` directly on loopback. Breaking: an image or deployment that never set `APP_ENV` now exits at start-up. `HOST` is no longer read; use `APP_HOST`. - **Bearer tokens are required in staging and production.** `APP_AUTH_MODE=none` is rejected there; `jwt` mode needs `APP_AUTH_ISSUER`, `APP_AUTH_AUDIENCE`, an HTTPS `APP_AUTH_JWKS_URL` and `APP_IDENTITY_HASH_KEY`.
- **`user_id` and `X-User-Id` are ignored in jwt mode**; the verified `(iss, sub)` is the identity. They remain only for `APP_AUTH_MODE=none` local development.
- **0.3.x threads are not accessible in jwt mode**: ownership is an HMAC of the verified identity, and there is no fallback to the old hash (`OPERATIONS.md`).
- New `401 authentication_error`, `403 authorization_error`, `503 authentication_unavailable`, `429 quota_exceeded` and `429 too_many_concurrent_runs` responses.
- `/v1/*` responses are `Cache-Control: no-store` (streams were `no-cache`); API docs are hidden in staging and production by default.

Changes:
- ADR 0006 defines OAuth 2.0/OIDC JWT authentication, principal identity, authorization and the migration from 0.3 (#52).
- JWT bearer authentication on every `/v1/*` route: JWKS-backed signature checks, issuer/audience/time-claim validation, an asymmetric-algorithm allow-list, token size limits, throttled key refresh, fail-closed JWKS errors and RFC 6750 responses. Health endpoints stay public (#53).
- Threads are owned by a keyed HMAC of the verified issuer and subject (#54).
- Scope-based authorization (`agent:invoke`, `threads:read`, `threads:delete`, `tools:calculator`), with optional role-to-scope mapping; tool availability follows the caller's permissions (#55).
- Per-user limits: per-principal rate limits, concurrent-run caps and rolling token budgets (#56).
- Privacy-safe security audit events on a separate `neuron_agent.audit` logger (#57).
- LangGraph Agent Server deployments use the same verifier, owner keys and permissions (#58).
- User data rights: `GET /v1/me/threads`, `GET /v1/me/export` and `DELETE /v1/me/threads` (#59).
- Authentication documentation and local development tokens (#62):
  - `make dev-auth`, `make dev-jwks` and `make dev-token` (`scripts/dev_token.py`) mint tokens from a local key and serve its JWKS on loopback, with no identity provider. They refuse to run unless `APP_ENV=development`;
  - README authentication quickstart, bearer `curl`/JavaScript examples and "Migrating from 0.3.x"; `OPERATIONS.md` identity-provider setup, key rotation and JWKS caching, `APP_IDENTITY_HASH_KEY` rotation, and runbook entries for each new error code; `SECURITY.md` IdP trust assumptions and remaining limitations;
  - a test that keeps `.env.example` in step with `Settings`.
- `/v1/me/threads`, `/v1/me/export` and `DELETE /v1/me/threads` do work in proportion to the page they return, not the caller's whole checkpoint history (#76):
  - on Postgres, one paginated aggregate query lists the caller's threads, served by a new `neuron_checkpoints_owner_idx` index. Re-run `make db-setup` when upgrading;
  - messages are loaded only from the latest checkpoint of each returned thread;
  - export stops reading once `APP_USER_DATA_EXPORT_MAX_BYTES` is exceeded;
  - bulk erase loads no messages.
- HTTP surface hardening for browser and multi-user exposure (#60):
  - CORS through an explicit `APP_CORS_ALLOWED_ORIGINS` allow-list (empty by default; `*` and malformed origins are rejected at startup), with preflight support for `/v1/agent/stream`;
  - `/docs`, `/redoc` and `/openapi.json` are hidden in staging and production unless `APP_EXPOSE_API_DOCS=true`, and the schema declares the bearer scheme;
  - `nosniff`, `no-referrer` and a deny-all `Content-Security-Policy` on every response, `Cache-Control: no-store` on `/v1/*` (streams change from `no-cache`), and opt-in HSTS (`APP_HSTS_MAX_AGE_SECONDS`);
  - an `APP_ALLOWED_HOSTS` Host check that exempts `/health/*`;
  - unhandled errors become a JSON `500 internal_server_error` that keeps the CORS, correlation and security headers;
  - rate limits match routes without any `root_path` prefix, so `uvicorn --root-path` no longer bypasses them, and failed authentication on `/v1/me/*` now counts against the per-IP limit like the other `/v1` routes;
  - `413` and `429` responses now carry `X-Correlation-ID`, and their log events carry the `request_id`;
  - an empty `X-Correlation-ID` is now replaced with a UUID instead of being logged as an empty ID.
- Security tests and eval dataset v3 for multi-user isolation (#61):
  - shared JWT fixtures (local RSA and EC keys, an in-process JWKS, `make_token`);
  - an HTTP BOLA matrix over every `/v1/*` route, including token expiry mid-session, revoked permissions and parallel streams;
  - a token-attack suite;
  - 12 multi-user security eval cases;
  - a `pip-audit` dependency audit in `make security` and CI.
- PyJWT is upgraded to 2.15.1 (14 advisories against 2.13.0, including algorithm confusion and JWKS redirects) and urllib3 to 2.8.0. A token whose `alg` doesn't match its `kid`'s key now gets `401` instead of `500`: the verifier passes the `PyJWK` to `jwt.decode`, which binds verification to the key's algorithm. Tokens with an empty or non-string `iss`/`sub` are now audited as `auth_failed` (#61).
- A model provider account with no API credit (OpenAI `429 insufficient_quota`) is no longer retried or reported as a rate limit. It fails at once as `ProviderQuotaError` (`provider_quota_exhausted`, `503`, alerting) (#50).
- Release gate (#63). It found and fixed one defect present since #58: on Agent Server, the graph built each run's authorization from the run's client-supplied `context`. Runs without one crashed, so every Agent Server and Studio run failed, and a run whose `context` listed `permissions` got those permissions (a function-level authorization bypass for tools). Runs now take permissions and the owner only from the authenticated user Agent Server records; client `context` grants nothing.

Known issues (see `docs/releases/v0.4.0-release-verification.md`):
- The live OpenAI smoke tests and live evals have still not run, for two reasons: no usable API credentials (as in 0.3.0), and, since #54, the root test conftest cleared `OPENAI_API_KEY` before collection so live tests skipped even with a key set (fixed in #83, after this release). Model-facing behaviour is verified only with fake models.
- Agent Server (`langgraph.json`) deployments enforce authentication, scopes, tool permissions and owner isolation, but not the API's per-principal rate limits, run caps, token budgets or message input policy.
- A newly published IdP signing key can be rejected for up to 30 seconds (PyJWT's forced-refetch cooldown); pre-publish keys.

## 0.3.0

"Stateful + Streaming": multi-turn conversations and real-time responses (ADR 0005).

- ADR 0005 records the design: checkpointer selection, thread rules, atomic turns, history bounds, the SSE protocol, the concurrency policy, and data retention. It partially supersedes ADR 0002 (#20).
- Configurable thread persistence through `APP_CHECKPOINTER`: `auto` (the default), `memory`, `postgres` or `none`. Postgres uses `AsyncPostgresSaver` over a validated connection pool opened in the FastAPI lifespan, with `make db-setup` migrations, readiness that reflects database health, and a `PersistenceError` (`503`) error type (#21).
- Multi-turn conversations: the server mints UUID thread IDs, each thread is bound to its hashed `user_id` (`404 thread_not_found` for missing and foreign threads alike), turns commit atomically, and the nested agent's internal state is never checkpointed (#22).
- Bounded history: a model-input token budget (`APP_MAX_HISTORY_TOKENS`) that never splits tool pairs, and a stored-message cap (`APP_MAX_THREAD_MESSAGES`) that evicts whole turns (#23).
- `POST /v1/agent/stream`: server-sent events (`run_started`, `token`, `tool_call`, `final`, `error`, `done`) with answer-field token extraction from structured output. Tool arguments are never streamed (#24).
- Cancellation and concurrency: client disconnects cancel the run, `APP_RUN_TIMEOUT_SECONDS` bounds whole runs, a busy thread gets `409 thread_busy`, `APP_MAX_CONCURRENT_STREAMS` caps open streams, and shutdown closes streams gracefully. Includes fixes for an anyio cancellation bug that kept model calls running after a disconnect, and a lease leak (#25).
- Thread history and lifecycle API: `GET /v1/threads/{id}/messages` and `DELETE /v1/threads/{id}`, plus `make prune-threads` retention through `APP_THREAD_RETENTION_DAYS` (#26).
- Streaming and state telemetry: stream lifecycle events with time to first token, termination reasons, turn and history size, and checkpoint latency and failure logging (#27).
- Eval dataset v2 (13 multi-turn cases), conversation security tests, and a live streaming smoke test. `neuron-eval` writes clean JSON to stdout again (#28).
- Operations documentation: Postgres, reverse-proxy settings for SSE, runbook entries, a `docker compose` stack with Postgres, and the full `.env.example` (#29).
- Release verification (#30) found and fixed a defect present since 0.2.0: every Agent Server or LangGraph Studio run failed, because inputs without a `run_id` crashed `agent_invocation_config`.

Known issue: the live OpenAI smoke tests and live evals could not complete, because the available API account had no credit (`429 insufficient_quota`). Deterministic suites, Postgres integration and real-server checks all pass; see `docs/releases/v0.3.0-release-verification.md`.

## 0.2.0

"Reliable Agent Runtime" — predictable failures, bounded execution, and operational visibility.

- Runtime error taxonomy: `AppError` subclasses with stable codes, HTTP mapping, retryability, and visibility metadata (#1).
- Enforced runtime limits: request/tool timeouts, agent iteration cap, prompt/body size limits (#2).
- Bounded provider retry with exponential backoff and jitter for transient model-provider failures (#3).
- Hardened tool execution boundaries: per-call timeout and failure isolation so a tool bug can never crash the agent loop (#4).
- Hardened request validation: body size limits, rejected-unknown-fields policy, control-character rejection (#5).
- Application-level token-bucket rate limiting at `/v1/agent/invoke`, keyed by client IP, with `429`/`Retry-After` (#6, ADR 0004).
- Expanded failure-and-resilience regression test suite covering every classified failure mode (#7).
- Agent evaluation dataset v1 with deterministic shape checks and live agent-quality scoring (#8).
- Structured logging and error telemetry: correlation IDs (`request_id`/`thread_id`/`run_id`) propagated via `structlog` contextvars and the LangSmith trace, plus `model`, `error_type`, `duration_ms`, and `retry_count` on key log events (#9).
- Documented reliability behavior and operations: timeout/retry/rate-limit configuration, the full failure-response taxonomy, production configuration expectations, and local troubleshooting across `README.md`, `OPERATIONS.md`, `DEVELOPMENT.md`, `SECURITY.md`, `ARCHITECTURE.md`, and ADR 0003 (#10).
- Fixed a defect found during release verification: the documented no-credentials fallback (a fake local chat model) crashed every `/v1/agent/invoke` call, because `create_agent` always binds tools and the fake model didn't support it (#11).
