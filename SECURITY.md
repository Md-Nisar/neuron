# Security

## Threat Model

Primary risks are prompt injection, unsafe tool use, sensitive logging, SSRF, dependency vulnerabilities, accidental exposure of provider secrets, and unauthorized access to persisted conversations. In staging and production, callers must authenticate through the configured external identity provider; human users and service accounts use the same bearer-token verification and scope-based authorization path. v0.4.0 trusts one configured issuer per deployment.

## Trust Boundaries

- User input is untrusted.
- Bearer tokens are untrusted until signature, issuer, audience, time claims, and required subject are verified against the configured issuer and JWKS.
- Verified `(iss, sub)` is the principal identity; request body fields and `X-User-Id` are not identity sources in JWT mode. Service accounts have no alternate header or bypass.
- The identity provider is trusted to authenticate users, to keep each `sub` stable and never reassign it to another person (a reused subject inherits the previous owner's threads), to grant scopes and roles correctly, and to protect its signing keys. Neuron cannot detect a failure of any of these.
- The configured identity provider and its JWKS endpoint are external trust dependencies. Key-fetch failure without a usable cached key fails closed; JWKS URLs must use HTTPS outside development. Each token is verified with the algorithm bound to its `kid`'s JWK: the JWK's `alg`, or, when that is absent, the default for its key type and curve (RS256 for RSA, ES256/ES384/ES512 for P-256/P-384/P-521). A token whose `alg` differs is rejected, even if `APP_AUTH_ALGORITHMS` allows it, so an identity provider that signs with RS384 or RS512 must publish `alg` in its JWKS.
- A thread UUID is not authorization. Invoke, stream, history, and delete enforce ownership from the verified principal and return the same not-found response for absent and foreign threads.
- Legacy v0.3 SHA-256 owner values are not accepted in JWT mode. Operators must follow ADR 0006's retention or separately reviewed re-key procedure; no dual-hash fallback is permitted.
- Tool output is untrusted.
- Retrieved or external content is untrusted.
- The system prompt is guidance, not an enforcement mechanism. It can be disclosed, so it must never contain secrets. An output guard (`security/output_policy.py`) is a defence in depth: it replaces an answer that reproduces eight or more consecutive words of the loaded prompt with a fixed refusal (#124, ADR 0003 addendum). It does not stop a paraphrase, a translation or a few words at a time.
- Enforcement must happen in code and infrastructure.

## Current Controls

- Typed request validation with Pydantic, including a request body size limit counted on the bytes received (chunked bodies included, before authentication; #137), a rejected-unknown-fields policy, and control-character rejection in user messages.
- Centralized settings and `.env.example`.
- Read-only initial tools.
- Scope-based function authorization: `/v1/agent/*` requires `agent:invoke`, thread history requires `threads:read`, thread rename requires `threads:write`, and thread deletion requires `threads:delete`. JWT permissions come from the configured `APP_AUTH_SCOPE_CLAIM` (space-delimited string or list, with `scp` fallback) and optionally explicit `APP_AUTH_ROLE_PERMISSIONS` mappings. Missing/unknown claims grant nothing; denied requests return `403 authorization_error` with `insufficient_scope`.
- Tool capabilities are filtered from model-visible tools per run and checked again immediately before execution. `utc_now` is public; `calculator` requires `tools:calculator`. A denied call (a missing permission or an unknown tool) never runs: it emits the `authorization_denied` audit event and a policy-block metric, and the model gets a fixed-text tool error, so the run completes instead of failing with `403`. Permissions and the verified principal travel only in runtime context, never prompts or checkpoint state. `AUTH_MODE=none` grants the documented development permission set.
- AST-based calculator without `eval`.
- MCP server list (ADR 0009 decision 5; `tools/mcp/config.py`, `pins.py`): only the operator's file defines servers; Streamable HTTP over https to a public host (loopback only in development and test); no stdio, SSE or WebSocket; each exposed tool is pinned to a hash of its name, description and input schema and defaults to `mutating`; annotations never authorize. The client (`tools/mcp/client.py`) discovers pinned tools once at start-up; each call uses a new connection with the configured bearer token, no sampling/roots/elicitation/logging callbacks, text-only results capped at `APP_MCP_MAX_OUTPUT_BYTES`, and a fixed error message for anything unusable. A server's own error text is never shown to the model. The HTTP client drops a response as soon as it passes a byte limit (declared or counted; compressed bodies are refused so the count is of decoded bytes), follows no off-origin redirect and ignores proxy environment variables. `neuron-mcp-pin` escapes terminal control and bidirectional characters in what it prints for review. Accepted gap: a server may change what a tool *does* without changing its definition; pins cover definitions only.
- Approvals (ADR 0009 decision 6, graph level): every `mutating` tool pauses the run for `approve`/`reject` before it runs; no edit, no answer in the tool's place, so what runs is what was shown. Without a checkpointer such tools are not offered. A paused run's checkpoint holds its tool calls and results until thread deletion or retention. `POST /v1/threads/{id}/approvals/{approval_id}` (scope `agent:approve`) is a new run with its own lease, rate limit, token budget and timeout; the pending call is shown in full and cannot be edited; a missing, foreign or already-decided approval is one `404 approval_not_found` (checked again after the thread lease is held, so a decision is single-use); a thread with a pending approval answers `409 approval_pending` to a new message. `GET /v1/threads/{id}/approval` (scope `agent:approve`, read-only) returns the pending approval to a reloaded client, with the same `404` for a missing, foreign or absent approval. Audit events `approval_requested` (count of actions), `approval_read` (approval ID) and `approval_decided` (decision, approval ID); none carries tool arguments.
- Per-user memory store (ADR 0009 decision 7; `memory/store.py`, off by default): one namespace per HMAC owner key, IDs that are an HMAC of owner and text under the identity key (never a plain hash of what the user wrote), so another user's memories cannot be listed, forgotten or erased; text passes the user-message input policy and the operator's length and count limits; the app database role has DML on the `store` table and no schema rights; memory text is user data. Its tools (`memory/tools.py`): `remember` and `forget` need approval; `remember` accepts only text the user wrote in this conversation (checked in code, and an impossible call is never put to the user); the owner key comes from the run context, never an argument; `recall` returns notes as escaped JSON inside a block marked as data, so stored text cannot close it. `GET /v1/me/memories` and `DELETE /v1/me/memories[/id]` (scopes `memories:read`, `memories:write`) act on the caller's namespace only, so a foreign ID is the same `404` as an unknown one; export and erase-all include memories; audit events carry counts and IDs, never text; the routes share the per-principal rate limit.
- Staging and production start-up refuse unsafe v0.7.0 settings (ADR 0009 decision 10): memory without the Postgres checkpointer, `http` or loopback MCP servers, approval-gated MCP tools without the Postgres checkpointer, and (memory on) a missing or unusable `store` table. Covered by unit and Postgres integration tests only; no real staging or production run.
- Tool registry (`tools/registry.py`, ADR 0009 decision 4) and high-impact tool deny list. Every tool has one spec (scope, risk class `read` or `mutating`, source); the model-visible list, the scope check at execution, audit names and the build-time refusal of a `mutating` tool without approval all read it. `HIGH_RISK_TOOL_NAMES` is checked separately.
- JWKS URL host check (#138). In staging and production the JWKS URL goes through `validate_safe_url`, which reads literal hosts only. Accepted gap: a DNS name that resolves to a private range, and an HTTP redirect to one, are not caught (ADR 0008 decision 9).
- URL egress helper (`validate_safe_url`, #167; ADR 0008 decision 12). No tool fetches a URL today, and a test fails if a tool (or a package module it imports) uses a network or process library without calling the helper.
  - It does: accept only `http`/`https`; reject userinfo, any non-ASCII or `%`-escaped host (IDN hosts must be passed as `xn--` punycode; hosts are rejected, never normalised, so fullwidth or ideographic dots and homoglyphs cannot disguise a local name), whitespace, control characters and backslashes; reject `localhost`, `*.localhost`, `*.local` and any literal IP that is loopback, private, link-local, multicast, reserved, unspecified or not globally routable, including IPv4-mapped, NAT64 and 6to4 IPv6, decimal/hex/octal/short IPv4 forms and trailing-dot hosts.
  - It does not: classify names (it understands only ASCII literal hosts, so `.internal`, `.lan` or `metadata.google.internal` pass; the fetcher's DNS re-check must catch them); resolve DNS, so a public-looking name that resolves to an internal address passes; follow or check redirects; pin the connection to an address; or stop DNS rebinding. Every fetching tool must resolve the host once, reject any resolved address that fails the same checks, connect to that checked IP and re-validate each redirect target (or not follow redirects). This contract is in the helper's docstring and a test asserts it.
- Request user IDs are hashed before entering graph state in `AUTH_MODE=none`;
  JWT mode uses a keyed HMAC owner key derived from the verified principal.
- Conversation thread isolation (ADR 0005; v0.4.0 authentication and identity are defined by ADR 0006):
  - thread IDs are server-minted UUIDv4s, and malformed IDs are rejected;
  - a supplied thread must already exist and belong to the same effective owner;
  - a missing thread and another user's thread return the same `404 thread_not_found`, so thread IDs can't be probed.

  In v0.4.0 JWT mode, ownership is derived from the verified `(iss, sub)` principal through a keyed HMAC; request-provided identity fields cannot override it. The unauthenticated request identity remains available only in explicit `AUTH_MODE=none` development/test mode.
- Token-bucket rate limiting on `/v1/agent/*`, `/v1/threads/*` and `/v1/me/*`, keyed by the verified principal (by a pseudonymous HMAC of the client IP for failed authentication and in `AUTH_MODE=none`), returning `429` with `Retry-After` (ADR 0004). Per-principal concurrent-run caps and rolling token budgets return `429 too_many_concurrent_runs` and `429 quota_exceeded`.
- Local development tokens (`scripts/dev_token.py`, not part of the package) refuse to run unless `APP_ENV=development`; their key stays in the git-ignored `.dev/`, and their JWKS is served on loopback only.
- Bounded provider/tool timeouts and capped provider retries (`APP_REQUEST_TIMEOUT_SECONDS`, `APP_TOOL_TIMEOUT_SECONDS`, `APP_PROVIDER_MAX_RETRIES`) and an agent-loop recursion limit (`APP_MAX_AGENT_ITERATIONS`) as resource-exhaustion controls, alongside rate limiting (see `OPERATIONS.md`'s Timeouts and Retries section).
- Structured logging with no deliberate raw secret logging: log fields are limited to IDs, names, stable error codes/types, durations, and retry counts — never raw user prompts, tool arguments, exception text, or provider API keys (see `ARCHITECTURE.md#observability`). A model-chosen tool name that is not a registered tool is audited with unsafe characters replaced and cut to 64 characters (`audit_tool_name`).
- HTTP surface hardening (`OPERATIONS.md`'s HTTP Surface section):
  - CORS is off unless `APP_CORS_ALLOWED_ORIGINS` lists exact origins. `*` is rejected, because requests carry credentials in `Authorization`; credentialed (cookie) CORS is never enabled.
  - `/docs`, `/redoc` and `/openapi.json` return `404` in staging and production unless `APP_EXPOSE_API_DOCS=true`.
  - Every response carries `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'` (the docs pages, when served, keep the browser default). `/v1/*` responses are `Cache-Control: no-store`. HSTS is set through `APP_HSTS_MAX_AGE_SECONDS` and is required in production.
  - `APP_ALLOWED_HOSTS` rejects other `Host` headers with `400`; `/health/*` is exempt for platform probes.
  - A client `X-Correlation-ID` is logged and echoed only if it's 1-128 characters of `[A-Za-z0-9._-]`; anything else is replaced with a UUID. `X-Request-Id` is ignored.
- LangSmith governance (ADR 0007, section 5): tracing is off unless `APP_ENABLE_LANGSMITH=true`, and a shell `LANGSMITH_TRACING=true` is overridden and logged as `langsmith_tracing_overridden`. Outside `development`, trace inputs and outputs (prompts, answers, tool arguments and results) are hidden unless `APP_LANGSMITH_CONTENT_APPROVED=true`; with LangSmith disabled nothing leaves the service. Staging and production require `LANGSMITH_API_KEY` when it is enabled. This governs the service's own tracing only: Agent Server's platform tracing is governed by the platform (see `OPERATIONS.md`, LangSmith).
- Bandit security scan in CI.
- Dependency vulnerability audit: `make security` runs `pip-audit` against every locked dependency (`uv export` of `uv.lock`, all groups) after Bandit. See Dependency Vulnerabilities.

## Mutating Tools and Agentic Threats (v0.7.0)

Mutating tools now exist behind a fixed set of controls (ADR 0009): authorization outside the model (scope per tool), human approval for every `mutating` tool (`approve` or `reject`, no edit), approval IDs bound to the owner and thread and usable once, audit events (`approval_requested`, `approval_decided`, `authorization_denied`), and tests for unauthorized, duplicate and replayed decisions. Idempotency is per tool: `remember` is keyed by the hash of the note, so repeating it stores one note. A new mutating tool must add its own idempotency story and tests.

How the OWASP agentic risks that v0.7.0 touches are handled:

| Risk | Where it shows up | Control | Tests |
| ---- | ----------------- | ------- | ----- |
| ASI02 tool misuse | MCP and memory tools | scope per tool, `mutating` default for MCP tools, approval, size and timeout caps, `approval_when` refuses calls that cannot be valid | `test_mcp_abuse`, `test_approval_api`, `test_memory_tools` |
| ASI04 supply chain | MCP servers | operator-only server list, https to public hosts, SHA-256 pin of each tool definition, no stdio, no sampling, roots or elicitation, no redirects off origin, no proxy or compression | `test_mcp_abuse`, `test_mcp_pins` |
| ASI06 memory poisoning | per-user memory | `remember` saves only text the user wrote, approval before writing, owner from trusted context, notes returned as escaped data, per-user limits, user can list and delete | `test_memory_tools`, `test_memory_api`, `approval` and security evals |
| ASI09 trust in the agent | approvals | the user decides on the exact arguments that will run; the model cannot edit them or answer in the tool's place | `test_approval_api`, `test_approval_stream`, `approval` eval |

## Streaming Output Policy

`POST /v1/agent/stream` (ADR 0005) applies the same controls as `/invoke`: validation, body limit, rate limit, thread ownership. In addition:

- **Tool calls:** `tool_call` events carry the tool's **name only**. Tool arguments and tool results are never streamed; both are untrusted.
- **Tokens:** `token` events carry only the growth of the `answer` field of the structured output. Raw JSON and other fields aren't streamed.
- **System prompt disclosure:** the graph replaces a final answer that reproduces the system prompt with a fixed refusal (`refused: true`) before it is stored or sent, and logs `system_prompt_disclosure_blocked`, emits the `output_blocked` audit event and counts a `system_prompt_disclosure` policy block, none with any prompt or answer text. While streaming, the last eight words (tokens) are held back until they can no longer start a prompt quote, and nothing more is sent after a hit; short answers therefore arrive in one `token` event at the end.
- **Errors:** `error` events use the same visibility rule as HTTP errors: internal failures appear only as `internal_server_error`, never with exception text or stack traces.
- **Resource exhaustion:** runs are bounded by `APP_RUN_TIMEOUT_SECONDS`, `APP_MAX_CONCURRENT_STREAMS` and a send timeout. Disconnected clients' runs are cancelled.

## Conversation Data at Rest

With thread persistence enabled (`APP_CHECKPOINTER=memory` or `postgres`, ADR 0005), checkpoints store user prompts and model answers. Treat them as user data.

- **What is stored.** Per thread:
  - the user turns and final answers (`messages`);
  - per-run fields, including the latest raw `user_message`;
  - the hashed `user_id` of the owner.

  The nested agent's tool calls and tool results aren't checkpointed. LangGraph keeps a checkpoint per step, so earlier versions of the state remain until the thread is deleted.
- **Where.**
  - `memory`: process memory only, gone on restart.
  - `postgres`: the `checkpoints`, `checkpoint_blobs` and `checkpoint_writes` tables.
- **Deletion.** `DELETE /v1/threads/{thread_id}` removes every checkpoint of a thread, for the owner only. `DELETE /v1/me/threads` performs the same operation for all discoverable threads belonging to the caller, is idempotent, and reports busy threads that it skipped rather than racing an active run.
- **Export and listing.** `GET /v1/me/threads` returns paginated metadata summaries without content. `GET /v1/me/export` returns paginated user/assistant text only (no system prompts, tool calls, or tool output), capped by `APP_USER_DATA_EXPORT_MAX_BYTES` (default 5 MB). Both require `threads:read`; bulk erasure requires `threads:delete`. These endpoints audit `user_data_exported` and `user_data_erased` events. The cap applies to serialized response data; clients should use pagination for larger exports.
- **Legacy checkpoint coverage.** Owner discovery uses checkpoint metadata. Threads created before owner metadata was added are not included in list, export, or bulk erasure until a successful authenticated run writes a checkpoint with owner metadata. For those threads, use the known thread ID with the existing owner-checked history/delete endpoints, or perform an explicitly reviewed migration to backfill ownership metadata before bulk operations.
- **Conversation titles (ADR 0011).** A thread created by a run is titled from its first message (whitespace collapsed, 80 characters), filed under the HMAC owner key in `neuron_thread_meta` (migrations 13 and 14; process memory without Postgres). `GET /v1/me/threads` and `GET /v1/me/export` return it, and `PATCH /v1/threads/{id}` (`threads:write`; 1 to 80 characters, no control or invisible characters; audit `thread_renamed` without the title) renames it, with the same `404` for a missing or foreign thread. It is content: thread deletion, bulk erasure (which also removes the owner's titles whose thread is already gone) and `make prune-threads` remove it, and it never appears in logs, spans or metrics (`tests/security/test_thread_titles.py`). A title that cannot be stored never fails the run.
- **Answer ratings (ADR 0010 decision 6, #285).** `POST /v1/threads/{id}/runs/{run_id}/feedback` (scope `feedback:write`) takes `{score: -1 | 1, reason?}` where the reason is one of a fixed list that fits the score (`helpful`, `accurate` for up; `inaccurate`, `unhelpful`, `unsafe`, `other` for down). Free text and unknown fields are `422`. A missing or foreign thread is the same `404`. The rating is filed under the HMAC owner key in `neuron_feedback` (migrations 15 and 16; process memory without Postgres), once per (owner, run): the first rating stands and a repeat returns it and records nothing. The `run_id` is not checked against the thread's history (an old run's ID is not kept there): it only keys the caller's own rating, so a forged ID can only add to the caller's own ratings, within the per-principal rate limit; an ID already rated on another thread is refused. Each new rating is a `user_feedback` log event, a `feedback_recorded` audit event, a `neuron.feedback` span and a `neuron.feedback` counter by score (`up`/`down`) and reason, never with any content. Thread deletion, bulk erasure and `make prune-threads` remove the ratings. Forwarding to LangSmith (issue #104) is not done.
- **Retention.** `make prune-threads` deletes threads inactive for longer than `APP_THREAD_RETENTION_DAYS` (default `30`). Run it on a schedule; Postgres has no built-in TTL.
- **Coverage limits.** Erasure deletes checkpoints and associated writes/blobs from the active configured checkpointer. It does not purge database backups, provider-side retention, application/deployment logs, or audit records. Deleted or pruned threads persist in database backups until those backups expire; align backup retention with `APP_THREAD_RETENTION_DAYS`. Provider retention is controlled by the configured model provider and its account settings.
- **Encryption.** Encryption at rest is the database's responsibility (managed-service or disk encryption). LangGraph's `EncryptedSerializer` is available if application-level encryption is required; it isn't enabled by default.
- **Access.** Thread history is exposed through the owner-checked history endpoint and `/v1/me/export`. System prompts, tool calls and tool output are never returned. In v0.3.0, owner identity comes from the unauthenticated `X-User-Id` header or `user_id` in the body. In v0.4.0 JWT mode, it comes from the verified principal defined by ADR 0006.

## Guard Tables and Database Roles

ADR 0008 decisions 15 and 16.

- **Guard tables.** `neuron_run_leases` (run leases for `thread_busy` and the per-user cap) and `neuron_meta` (the identity key check value) sit beside the LangGraph tables. Leases hold an owner key (an HMAC) and a thread ID, never message content or the identity key. `neuron_meta` holds an HMAC of a fixed label under `APP_IDENTITY_HASH_KEY`, which does not reveal the key; the key itself is never stored.
- **Role split.** `neuron_migrator` owns the schema and is the only role that creates, alters or drops anything; it is used by `setup` alone. `neuron_app`, the web service and `prune`, gets DML only: `SELECT, INSERT, UPDATE, DELETE` on the checkpoint tables, `SELECT, INSERT, DELETE` on `neuron_run_leases`, nothing on `neuron_meta` or the two migration bookkeeping tables (the check value is an offline oracle for a low-entropy key, so use `secrets.token_urlsafe(32)` or better for `APP_IDENTITY_HASH_KEY`). It has no `CREATE`, `DROP`, `TRUNCATE` or ownership, so a SQL-level bug in the web process cannot drop or truncate a table, rewrite the identity check value or forge a migration record. Tests run this split against a real Postgres.
- **Operator-only CLIs.** `python -m neuron_agent.persistence.cli setup` and `prune` have no HTTP route and are never reachable through the API. `setup` runs as the migrator (`APP_POSTGRES_MIGRATION_DSN`); `prune` runs as the app role (`APP_POSTGRES_DSN`). `setup` stores the check value once and refuses a different key unless `--rotate-identity-key` is passed; its errors never print a DSN, key or check value. First write and rotation of the check value emit audit events (no key or value), and `--rotate-identity-key` must not stay in a permanent pre-deploy command. `setup` rejects `--older-than-days`, and `prune` errors are fixed text like `setup`'s.
- **Single role (staging only).** With one role the web process owns the schema and can drop tables (ADR 0008 decision 17). `setup` logs `app_role_grants_skipped`, and fails in production instead. Accepted for a disposable staging database only.
- **Driver logs are redacted (#204).** `psycopg_pool` logs connection errors on the `psycopg.pool` logger, and libpq can echo the whole DSN in them. `build_persistence` installs a `DsnRedactionFilter` (`persistence/dsn_redaction.py`) on the `psycopg` and `psycopg.pool` loggers that replaces the configured DSN and its password (also URL-decoded and `password=` forms) before any handler sees the record. The `setup` CLI never prints exception text. A DSN passed to some other logger or printed by other code is not covered.
- **Not covered yet.** The web process still holds `APP_POSTGRES_MIGRATION_DSN` where the platform shares the pre-deploy environment (ADR 0008 open question 20); only `persistence.cli` reads it, and a test pins that. In staging and production every start compares its `APP_IDENTITY_HASH_KEY` with the stored check value through the `neuron_identity_status` SECURITY DEFINER function (#139), which answers only match, mismatch or unset; the app role still cannot read the value. A holder of the app role can use that function as an online yes/no oracle for key guesses, so the key must be random with at least 128 bits of entropy (the 32-character setting minimum does not check entropy). Keep Postgres `log_statement` and `log_parameter_max_length_on_error` restrictive: a failed call logs its parameter, which is an HMAC of the key, not the key.
- **Checked in production.** Settings refuse equal runtime and migration DSN users. The web process (and `prune`) refuses to open its pool unless it is connected as `APP_POSTGRES_APP_ROLE` and that role is not a superuser, has no `BYPASSRLS`, is not a member of the schema owner and cannot `CREATE` in the schema. `setup` checks the same of the app role, plus that it is not a member of the migrator, and verifies the privilege matrix with `has_table_privilege` so silently ineffective grants fail it. Staging, which may use one role, skips these checks.

## Dependency Vulnerabilities

`make security` fails on any known vulnerability in a locked dependency (OWASP LLM03, supply chain). It resolves nothing itself: it audits exactly the versions pinned in `uv.lock`, using the PyPI advisory database.

When it fails:

1. **Upgrade.** If a fixed version exists, raise the lower bound in `pyproject.toml` for direct dependencies, or run `uv lock --upgrade-package <name>` for transitive ones. Then run all quality gates. Treat auth, crypto and HTTP-client libraries (`pyjwt`, `cryptography`, `urllib3`, `httpx`) as urgent.
2. **Ignore only with a reason.** If no fix exists, or the vulnerable code path isn't reachable from this project, add the ID to `AUDIT_IGNORES` in the `Makefile` and list it below with the package, why it doesn't apply, and a review date no more than 90 days out. On or after that date, re-check upstream and either upgrade or renew the entry with fresh reasoning.

Dependabot (`.github/dependabot.yml`) opens weekly, grouped update PRs for `uv`, `github-actions` and `docker` (base images), each after a 7-day cooldown. Nothing auto-merges, in Dependabot or any workflow (a test checks the workflows). Every `uses:` in `.github/workflows/` is pinned to a full commit SHA with a `# vX.Y.Z` comment, so a Dependabot PR is the only way a locked action version changes. Review these PRs like any other:

- **All gates apply.** `ci`, `ai-code-verification` and `codeql` must pass, and a person reads the diff and the upstream release notes. For an action, check that the new SHA belongs to the tagged release.
- **The 90-day rule applies to new packages only.** The `new-dependencies` job still rejects a package missing from PyPI or under 90 days old when a PR adds one; a version bump of a package already locked is not held to it.
- **`langgraph-checkpoint-postgres` bumps** also need the rollback test in `docs/rollback-test-checkpoint-postgres.md` (#143, ADR 0008 decision 7) before merging.

Current ignores: none.

### Image vulnerabilities

The `image-publish` workflow scans every image pushed from `main` (ADR 0008 decision 6) with Trivy, pinned by commit SHA, before it attests the digest. The scan fails on any fixable HIGH or CRITICAL finding in OS packages and the locked libraries (`ignore-unfixed`, severity `HIGH,CRITICAL`). Trivy's vulnerability database is downloaded at run time, on every run: caching is off, and a database update that fails fails the scan, so a stale or cached database never gives a pass. A new CVE can therefore fail a build that did not change.

When it fails, follow the same two steps as above: upgrade (a newer base image digest through Dependabot, or `uv lock --upgrade-package <name>`), or ignore with a reason. Image ignores live in one reviewed file, `.trivyignore.yaml`, as `vulnerabilities` entries with `id`, `statement` (why it does not apply, naming the package) and `expired_at`, a date no more than 90 days out. A test fails if an entry lacks any of them or the date is further out, and Trivy stops honouring an entry after its date. `AUDIT_IGNORES` and `.trivyignore.yaml` are separate: one audits locked Python packages, the other the built image.

Image ignores: none.

What the pipeline does not prove: an attestation shows where and how the image was built, not that tests passed. ADR 0008 decision 6 step 1 (the `ci` gates) is not wired into `image-publish.yml`, so promotion (a later issue) must require a green `ci` for the digest. Deploy by digest only: `sha-<sha>` is a mutable tag, and a re-run of the workflow re-points it to a new digest. The Trivy binary (v0.70.0) is downloaded by tag at run time by the pinned `setup-trivy` and is not hash-pinned (accepted risk), and the SHA-pin test does not cover actions nested inside pinned composite actions. `provenance: mode=max` records build arguments and context metadata, which is fine while the repository is public; revisit it if the repository becomes private.

## Browser Application (v0.8.0)

The web application (`web/`, ADR 0010) puts model output, tool output and the user's own data in front of a person, in a page that holds a bearer token. The threat model:

| Threat | Control | Where it is tested |
| --- | --- | --- |
| Script injected through model, tool or user text | Everything is rendered as React elements: raw HTML stays literal text, no `dangerouslySetInnerHTML` (lint fails on it), code is text; a strict CSP without inline script or `eval` | `Markdown.test.tsx`, `ChatScreen.test.tsx`, `test_web_headers.py` |

Not covered, by design or by limit:

- **Script that runs on the app's origin can read the token in memory** and call the API as the user. The controls above exist to stop such script running; none of them helps once it does.
- **`sessionStorage` holds the sign-in transaction** (state, nonce, PKCE verifier) for up to ten minutes across the redirect. It is deleted when the callback arrives.
- **No Trusted Types.** `require-trusted-types-for 'script'` is not set because it could not be tried in a real browser here.
- **Nothing was enforced by a real browser.** The CSP is tested as a policy and the source is checked against it; no Playwright run has loaded a built page under the headers. Silent renew is likewise unproven in a browser (`web/README.md`).

## Remaining Limitations

- **No token revocation.** Tokens are verified locally (no introspection), so a stolen access token works until it expires. Keep access-token lifetimes short at the IdP. A stream's token is checked once, when it starts.
- **One issuer per deployment.** The owner key joins issuer and subject without length-prefixing; supporting several issuers needs that changed first.
- **Per-process limits.** With `APP_LIMITS_BACKEND=memory`, rate limits, concurrent-run caps and token budgets are in memory per worker and reset on restart; they aren't shared across replicas. With `postgres` the run guard and the token budget are shared and durable (ADR 0008 decision 8): the budget reserves tokens at admission and settles to real usage, in an owner-keyed ledger (`neuron_token_ledger`) that holds HMAC owner keys and token counts per minute, no content, and is deleted outside the window by the retention job. Both fail closed (`503`) on a database error. The request rate limiter is shared too (#148): one `UNLOGGED` token-bucket table, `neuron_rate_buckets`, written once per rate-limited request with database-clock timestamps and failing closed (`503`) like the other guards. Its `ip:` keys are HMACs of the client address (IPv6 as its /64) under a key derived from `APP_IDENTITY_HASH_KEY` with HKDF and its own label, so no raw address is stored; they are **pseudonymous, not anonymous**: the IPv4 space is only 2^32, so anyone holding the key can reverse a key by brute force, and the table is therefore personal data (idle rows are deleted as the limiter writes and by the retention job). An `UNLOGGED` table is empty after a crash, an unclean shutdown, a failover or a point-in-time restore, which grants every caller one fresh burst. Whether this data is in the user-data rights scope: `principal:` rows are keyed by the owner key, and the user-data export and erasure do not read or delete them; an erased user's row is removed by idle deletion (as the limiter writes, and by the daily retention job) at most about `APP_RATE_LIMIT_BURST / refill rate` seconds after their last request (the daily job removes only rows idle over an hour, so a quiet system clears within about a day), and it holds no content. `ip:` rows cannot be attributed to a person without the key and are deleted the same way. A small in-memory IP limiter runs in front of it for unauthenticated and failed-authentication traffic, so a flood from one address is refused without a database write per request. The budget is enforced at admission and settled afterwards; there is no mid-run enforcement, so one run can overshoot by its real cost (agent iterations, thread history, tool output; history is trimmed to `APP_MAX_HISTORY_TOKENS` per model call, which bounds each call but not the number of calls), and the excess is charged when the run settles. A run that reports no usage keeps its whole reservation. Settlement is idempotent (a retry after an ambiguous commit cannot subtract twice), but a reserve cancelled after its commit leaves its reservation counted until the window passes (conservative).
- **`typ` check.** With `APP_AUTH_REQUIRE_TYP=true`, only `at+jwt` is accepted, not the `application/at+jwt` spelling RFC 9068 also allows.
- **`APP_IDENTITY_HASH_KEY` exposure** lets someone with database access link threads to known identities. It grants no access by itself. Rotation orphans every thread (`OPERATIONS.md`).
- **Output guard is verbatim only.** It matches runs of eight words after case, markdown and punctuation are normalised. A paraphrase, translation, encoding or answer spread over several turns passes, as does character-level obfuscation (homoglyphs, or punctuation or spaces between letters); zero-width and other format characters are ignored. A quote in a streamed preamble that the stream guard stops, while the final answer is clean, leaves no log or audit record. On Agent Server the guard covers the stored and final state only: a client reading `stream_mode=messages` receives the model's live chunks unguarded. A normal answer that repeats the prompt's opening line is refused. Tokens already streamed before a hit (up to seven consecutive prompt words) cannot be recalled.
- **Development tokens trust loopback.** In development the API fetches the JWKS over plain HTTP from `127.0.0.1:8765`, so on a shared machine another local user who binds that port first can mint tokens the development API accepts. Use them on single-user machines.
- **Agent Server runs skip the API-layer guards.** Authentication, scopes, tool permissions and owner isolation apply on both deployment paths, but the per-principal rate limits, concurrent-run caps, token budgets and the message input policy (length, control characters) live in the FastAPI app and `AgentService`, so `langgraph.json` deployments don't get them. Use the platform's own limits there.
- **Signing-key rotation window.** A newly published key can be rejected for up to 30 seconds (PyJWT's forced-refetch cooldown); IdPs should pre-publish keys (`OPERATIONS.md`).
- **Readiness and the IdP.** `/health/ready` marks an instance not ready after a request's JWKS fetch fails, and re-probes the JWKS (at most once per 5 seconds per process) while not ready, so health checks alone bring it back once the IdP answers. Tokens signed with a cached key keep verifying and the instance stays ready during an outage; a token with an uncached `kid` (including a forged one) is refused with `503` but doesn't change readiness while cached keys are usable (`OPERATIONS.md`).
- **Injected tool calls the security eval can't see.** A prompt-injected call to a tool the caller is permitted to use, or a denied tool attempt, doesn't fail a security eval case; denied calls are absent from `used_tools` (`EVALUATION.md`).
- **Denied tool calls are not `403`s.** The `authorization_denied` audit event (`resource_type=tool`) and the `insufficient_scope`/`unknown_tool` policy-block metric are the only signals of an injected tool attempt. The example alert `NeuronDeniedToolCallsSpike` (`deploy/observability/prometheus-alerts.yaml`; runbook in `OPERATIONS.md`) fires on more than ten of those policy blocks in 10 minutes; a handful stays below it, so review the audit events too.
- **Reference deployment (Render, #150).** The web service holds `APP_POSTGRES_MIGRATION_DSN` (schema owner) because Render's pre-deploy command shares its environment, so an environment dump or RCE in the web process exposes owner-equivalent credentials; the cron job also holds the provider and identity keys because `prune` loads full settings. The OTLP Collector accepts unauthenticated traffic from its private network, so staging and production must live in separate workspaces. Accepted for now; see ADR 0008 open question 20.
- **v0.7.0 not exercised in staging or production.** Approvals, MCP, memory and the Anthropic provider are unit-, graph- and integration-tested (Postgres 16 locally) and verified with fakes or the NVIDIA development model. Anthropic was never called live (no funded key). Production and staging settings are validated but unrun.
- **MCP trust is the pin, not the server.** A pinned definition proves the tool is the one reviewed, not that the server behaves well. Results are untrusted data, but a server that is allowed a tool can still return misleading text; mark anything with side effects `mutating`.
- **Memory concurrency.** The item limit is checked before the write, so concurrent writes by one user can exceed it by the number in flight. Memory is not available on the Agent Server path.
- **`AUTH_MODE=none` is unauthenticated.** Any caller can claim any `user_id`. Settings reject it in staging and production; `make api` binds to `127.0.0.1`, and `neuron-api` refuses a non-loopback bind unless `APP_ENV` is set explicitly. Accepted residual risk: an explicit `APP_ENV=development` on a public host still serves unauthenticated.
