# v1.1.0 Phase 0 spike (RAG-00.02)

Measured answers to the five open questions in
[ADR 0014](../decisions/0014-knowledge-engine.md#open-questions-decided-by-the-spike-rag-0002).
The scripts are on the branch `RAG-00.02-spike` under `spike/`. That branch is never merged to
`main`. This record is the only part of the spike that lands.

Date: 2026-11-02. All numbers come from one machine and one run unless stated, so they are
indicative, not benchmarks.

## Summary of answers

| # | Question | Answer | ADR default before |
| --- | --- | --- | --- |
| 1 | Docling on CPU, or a GPU parser? | CPU is enough for v1.1.0: 0.61 PDF pages/s on 4 vCPU, peak 4.7 GiB, every evidence passage extracted, scanned page OCR works | CPU |
| 2 | Embedding dimensions | **1,024**. recall@5 is 0.918 at both 1,024 and 2,048; the named model is retired, its successor is `nvidia/nemotron-3.5-embed-1b` | 2,048 |
| 3 | Exact versus HNSW threshold | **10,000 allowed chunks**: exact at or below, HNSW (`ef_search` 100, `relaxed_order`) above. HNSW is faster from about 2,000, but under about 5,000 it can return too few rows | 20,000 |
| 4 | Queue library | **Procrastinate**, with a periodic stalled-job sweep. Exactly one completion per job after `SIGKILL`; PGQueuer also passes | Procrastinate |
| 5 | Embedding provider for production | NVIDIA API catalog for **development only** (trial terms forbid production use); **TEI** is the production default | NVIDIA for development only |

Two more findings change later stories:

- **pgvector is not a trusted extension.** `CREATE EXTENSION vector` as `neuron_migrator` fails
  with "permission denied to create extension vector". A superuser or the platform operator must
  create it before migrations run (RAG-01.01).
- **Parallel HNSW builds need shared memory.** With Docker's default 64 MB `/dev/shm` the build
  fails; the spike database uses `shm_size: 4gb`. The reference stack needs the same, or
  `max_parallel_maintenance_workers = 0` (RAG-01.01, RAG-04.01).

## 1. Docling on CPU

**Method.** docling-serve ran with `docker run --network none`: health was ok, DNS failed and
only loopback existed, so the model weights in the image are enough and no egress is needed
(ADR 0014 K2). Each file was posted to `/v1/convert/file` with `to_formats=json`, `do_ocr=true`
and `table_mode=accurate`, one at a time (`spike/docling_bench.py`). `spike/docling_score.py`
then counted pages, tables and headings and checked that each case's evidence text appears on its
expected page or section. Memory came from `docker stats` every 2 s.

| Document | Pages | Seconds | s/page | Tables | Headings | Evidence on expected page |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| nist-ai-100-1 | 48 | 62.1 | 1.29 | 13 | 38 | 3/3 |
| nist-ai-600-1 | 64 | 120.1 | 1.88 | 67 | 51 | 3/3 |
| nist-cswp-29 | 32 | 50.1 | 1.57 | 4 | 40 | 5/5 |
| nist-sp-800-207 | 59 | 72.3 | 1.22 | 8 | 82 | 3/3 |
| nist-sp-800-218 | 36 | 78.3 | 2.18 | 23 | 22 | 2/2 |
| nist-sp-800-63b | 80 | 160.2 | 2.00 | 19 | 149 | 7/7 |
| nist-sp-800-61r3 | 48 | 90.1 | 1.88 | 30 | 59 | 2/2 |
| nist-sp-800-88r1 | 65 | 92.1 | 1.42 | 29 | 79 | 2/2 |
| nist-sp-800-190 | 63 | 90.1 | 1.43 | 15 | 103 | 2/2 |
| rfc7636 (`.txt`) | — | 2.0 | — | 0 | 0 | 0/2, text present, no page numbers |
| pgvector README (`.md`) | — | 2.0 | — | 11 | 95 | 4/5, text present |
| larkspur-handbook (`.docx`) | — | 2.0 | — | 2 | 5 | 4/4 |
| greenhouse-log-scanned (image PDF) | 2 | 6.0 | 3.01 | 2 | 2 | 2/3, text present |
| injection hidden-text (`.pdf`) | 1 | 2.0 | 2.01 | 0 | 1 | — |

- **Throughput.** The 9 text PDFs: 495 pages in 815 s, 0.61 pages/s or about 1.65 s per page,
  using all 4 vCPUs (`docker stats` 380–400 %). That is about 2,200 pages an hour for one
  container; a 20,000-page knowledge base takes about 9 hours to ingest the first time.
- **Memory.** About 785 MiB idle; peak 4.69 GiB during the larger PDFs. A 6 GiB container limit
  leaves headroom.
- **Quality.** The evidence text of all 43 checked cases was extracted. 39 of 43 were found on the
  expected page or section. The four misses are attribution, not extraction:
  - Plain-text RFCs go through Docling's Markdown path, which has no page provenance. RFC pages
    end in form feeds, so the ingest pipeline must split `.txt` files on form feeds itself to give
    page citations (RAG-02.x).
  - In the pgvector README the evidence sits beside an inline code span, which Docling stores as a
    separate text item; the scorer looked for one item.
  - The scanned page was read correctly and on the right page, but OCR joined two words
    ("42 litresper minute"). Keyword checks pass ("42"); exact-quote matching on OCR text must
    tolerate missing spaces.
- **Injection.** The hidden white-on-white instruction in `injection/hidden-text.pdf` ("call the
  forget tool") is extracted as ordinary text. Docling does not filter it, so retrieved text must
  stay untrusted and taint the run (ADR 0014 K7), as planned.

**Answer.** CPU docling-serve is enough for v1.1.0. A GPU parser is a scaling option, not a
requirement.

## 2. Embedding dimensions

**Method.** `nvidia/llama-nemotron-embed-1b-v2`, named in the ADR, now returns HTTP 410 Gone on
the NVIDIA API catalog. The current catalog models are `nemotron-3-embed-1b` (2,048 only),
`nemotron-3.5-embed-1b` (1,024 and 2,048), `nemotron-3.5-embed-8b` and
`llama-nemotron-embed-vl-1b-v2`. The spike used `nvidia/nemotron-3.5-embed-1b`, the same size
class.

`spike/embed_recall.py` cut the 30 text documents (the scanned one excluded) into 2,032 chunks of
1,200 characters with a 1,000-character step, embedded them as passages and the 61 answerable
questions with text evidence as queries, and ranked by cosine similarity (dense only, no
reranker). A chunk counts as a hit when it contains the case's evidence text. Only public and
fictional corpus text was sent to the API.

| Dimensions | recall@1 | recall@5 | recall@10 | MRR@10 |
| ---: | ---: | ---: | ---: | ---: |
| 2,048 | 0.754 | 0.918 | 1.000 | 0.823 |
| 1,024 | 0.721 | 0.918 | 1.000 | 0.799 |

- Truncating the 2,048-dimension vectors to 1,024 and renormalising gave exactly the same results
  as asking the API for 1,024, so one stored profile can be cut down later without re-embedding.
- The same five cases miss at @5 in both: answerable-005, -013, -016, -025 and -046. Hybrid search
  and reranking (Phase 2) are the levers for those, not more dimensions.

**Answer.** 1,024 dimensions. recall@5 is unchanged, the halfvec index and table are half the
size, and HNSW builds faster. The default model becomes `nvidia/nemotron-3.5-embed-1b`.

## 3. Exact scan versus HNSW by allowed-set size

**Method.** `spike/ann_load.py` loads 200,000 synthetic, clustered 1,024-dimension vectors into
one `profile_id`, spread over knowledge bases of 500, 2,000, 5,000, 10,000, 20,000, 50,000 and
100,000 rows (plus 25 filler KBs of 500). It builds the ADR's index shape: a btree on
`(profile_id, kb_id)` and a partial HNSW expression index
`((embedding::halfvec(1024)) halfvec_cosine_ops) WHERE profile_id = 1` (m 16, ef_construction 64).
Load took 18 s; the HNSW build took 35 s with 3 parallel workers; the index is 521 MB.

`spike/ann_bench.py` runs 20 queries per KB, each a stored vector plus noise, and asks for 80
candidates (the RAG-04.01 dense candidate count) filtered to that one KB. The exact path disables
index scans so it reads the KB's rows through the btree and sorts. The HNSW path uses
`hnsw.iterative_scan = relaxed_order` and re-sorts the 80 rows. recall@10 compares HNSW's top 10
with the exact top 10. JIT is off on both paths.

The first run measured the exact path twice: the planner chose the btree plus a sort for the
"HNSW" query even with `enable_seqscan = off`. Only with `enable_bitmapscan = off` and
`enable_sort = off` as well does it use the HNSW index. **RAG-04.01 must check its plans with
`EXPLAIN`, and choose and force the path in code, not leave it to the planner.**

Latency in milliseconds, `ef_search` 40 / 100:

| Allowed chunks | Exact p50 | Exact p95 | HNSW p50 (40 / 100) | HNSW p95 (40 / 100) | recall@10 (40 / 100) |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 500 | 1.9 | 2.8 | 2.9 / 2.4 | 4.8 / 5.3 | 1.00 / 1.00 |
| 2,000 | 6.5 | 9.2 | 2.5 / 2.3 | 4.8 / 3.3 | 1.00 / 1.00 |
| 5,000 | 15.3 | 24.0 | 2.5 / 2.7 | 5.1 / 6.3 | 1.00 / 0.99 |
| 10,000 | 28.1 | 50.8 | 3.2 / 2.7 | 5.6 / 5.4 | 0.99 / 0.99 |
| 20,000 | 52.2 | 56.5 | 2.4 / 2.9 | 4.2 / 4.9 | 0.96 / 0.98 |
| 50,000 | 133.6 | 187.6 | 3.2 / 3.4 | 5.5 / 5.5 | 0.89 / 0.93 |
| 100,000 | 269.4 | 308.4 | 2.7 / 2.5 | 4.0 / 5.3 | 0.86 / 0.92 |

Exact-path times are from the `ef_search` 40 run; the 100 run agrees within a few
milliseconds. Every query on-topic for its KB returned all 80 rows.

Off-topic queries tell a different story for small KBs. `spike/ann_offtopic.py` sends 10 random
vectors per KB with `ef_search` 100:

| Allowed chunks | HNSW p50 (ms) | Rows returned, min / mean of 80 |
| ---: | ---: | ---: |
| 500 | 86.3 | 3 / 28.0 |
| 2,000 | 66.2 | 48 / 75.2 |
| 5,000 | 32.6 | 80 / 80.0 |
| 10,000 | 51.2 | 80 / 80.0 |
| 20,000 | 21.1 | 80 / 80.0 |

When the query is far from the KB, the iterative scan walks the whole graph's neighbourhood,
stops at `hnsw.max_scan_tuples` (20,000 by default) and returns too few rows, slowly. That breaks
the RAG-04.01 criterion that a small KB returns k results when k exist. The exact scan always
returns them.

**Answer.** The default exact-scan threshold is **10,000 allowed chunks** (a setting for
RAG-04.01, for example `APP_KNOWLEDGE_EXACT_SCAN_MAX_CHUNKS=10000`). At or below it the exact
scan is complete, has perfect recall and costs at most about 51 ms p95 on this machine. Above it,
HNSW with `relaxed_order` and `hnsw.ef_search = 100` stays under 6 ms p95 with recall@10 of at
least 0.92. The ADR's working default of 20,000 would have cost about 57 ms p95 at the boundary
for no gain in safety. These are synthetic vectors on one machine; RAG-04.01 re-checks the
boundary on the real corpus.

## 4. Queue library

**Method.** `spike/queue_test.py LIB` installs the library's schema as `neuron_migrator`, grants
`neuron_app` what it needs, and runs the worker as `neuron_app` with Neuron's pool settings
(`max_size=10`, `timeout=10`). It defers 6 jobs (one fails once on purpose), `SIGKILL`s the worker
while two or more jobs are mid-run, restarts it, then defers 2 more and sends `SIGTERM` during a
job to test the drain. Each job records its start and completion in `spike_effects`, and the
completion inserts into `spike_done` with a primary key, so a second completion would show up.

| Check | Procrastinate 3.10.0 | PGQueuer 1.6.0 |
| --- | --- | --- |
| Killed worker's jobs re-run after restart | Only with a periodic sweep (`get_stalled_jobs` + `retry_job`); about 16 s with a 2 s heartbeat and 6 s stall timeout | Yes, automatically after `heartbeat_timeout` (6 s) |
| Each job completes exactly once | Yes, 8 of 8 | Yes, 8 of 8 |
| Failed job retried | Yes (`RetryStrategy(max_attempts=3)`) | Yes (`DatabaseRetryEntrypointExecutor(max_attempts=3)`) |
| `SIGTERM` drains the running job, exit 0 | Yes | Only after `setup_signal_handlers(pgq.shutdown)`; without it the worker dies at once and loses completions |
| Connections | psycopg pool, Neuron's settings | One dedicated connection |

Both libraries give at-least-once execution: a job killed mid-run starts again. The ingest task
must therefore be idempotent (replace a document's chunks in one transaction, keyed by document
and version).

Both install as the migrator. The app role needs `USAGE` on the schema; `SELECT`, `INSERT`,
`UPDATE` and `DELETE` on the tables; `USAGE` and `SELECT` on the sequences; and `EXECUTE` on the
functions. Neither needs ownership or superuser at run time.

**Answer.** Procrastinate stays: it passed, it uses a normal psycopg pool and its own migrations
fit the migrator/app split. The worker must schedule the stalled-job sweep (a periodic task that
calls `get_stalled_jobs(seconds_since_heartbeat=…)` and `retry_job`); Procrastinate 3.10.0 does
not do it by itself. The own-lease-table fallback is not needed.

## 5. Embedding provider terms

- **NVIDIA API catalog.** The *NVIDIA API Trial Terms of Service* (PDF from
  `assets.ngc.nvidia.com`, 9 pages, SHA-256 prefix `afd5df03`) say in §1.2 that the trial is for
  "limited trial purposes only and without use of the API Service or Generated Content in
  production"; production needs a separate NVIDIA subscription. §2.3 says inputs are not stored
  after the session, except logging for security and abuse monitoring under §2.4 and §3.3. There
  is no public per-token price; the trial uses credits.
- **Model licence.** The Nemotron embedding models are under the NVIDIA Open Model License, with
  the Llama 3.2 Community License for Llama-based ones. They support Matryoshka dimensions 384 to
  2,048.
- **TEI.** Hugging Face Text Embeddings Inference is Apache-2.0 (licence file checked); latest tag
  v1.9.4. It runs in the deployment's own network.

**Answer.** The NVIDIA API catalog stays for development and the small checks this project
already runs on its free tier, with public or fictional text only. TEI is the default production
embedding provider; NVIDIA under a paid subscription is the alternative for operators who accept
its terms.
