# v0.9.0 "Production Candidate": Issue Drafts

These are drafts for the v0.9.0 milestone, taken from ADR 0012 (Proposed). They are not filed
on GitHub yet: they will be filed once the owner accepts the ADR, and from then on the issues
are the source of truth.

Each draft is sized for one PR of under about 400 changed lines. Everything is verified on the
local reference stack: the fake model with latency, a local Keycloak and the NVIDIA development
model. Staging and production are not exercised (owner decision, 2026-10-27).

Labels: the existing set, plus a `v0.9.0` label and `load`.

## Drafts

### 1. ADR 0012: production candidate
`architecture`, `documentation`, `priority:p0` · Depends on: none
- [ ] ADR 0012 is reviewed and set to Accepted, and its open questions are answered.
- [ ] `docs/ROADMAP.md` and `CLAUDE.md` link it. Their release status for v0.6.0 to v0.8.0
      is brought up to date: all three are tagged, with gates open and deferred.

### 2. Gate deferral record
`documentation`, `priority:p0` · Depends on: 1
- [ ] #160, #253 and #293, and every open child, get a comment listing the remaining exit
      criteria and a label `deferred:post-1.0`. None is closed.
- [ ] A table in `docs/ROADMAP.md` lists the deferred items and the release that owns each.

### 3. Reference stack
`deployment`, `dev-experience`, `priority:p0` · Depends on: 1
- [ ] `docker-compose.reference.yml` runs two API replicas from an image tag passed in (not
      `build: .`), with Postgres, Keycloak, `APP_AUTH_MODE=jwt`, Postgres limits and the
      Postgres checkpointer. All ports bind to loopback.
- [ ] The production settings profile is used. Each relaxation is commented with its reason
      (ADR 0012 open question 5).
- [ ] `make reference-up` and `make reference-down`. A script prints the running image
      digest, and a test checks the override (no `build:`, loopback ports, jwt mode).
- [ ] The smoke test passes against both replicas.

### 4. Fake model with latency
`testing`, `security`, `priority:p0` · Depends on: 1
- [ ] Three settings control the fake model: `APP_FAKE_MODEL_TTFT_MS`,
      `APP_FAKE_MODEL_TOKENS_PER_SECOND` and `APP_FAKE_MODEL_OUTPUT_TOKENS`. They are read in
      `config/settings.py`, bounded, and default to today's instant answer.
- [ ] Settings validation refuses them in `staging` and `production`. A test covers each
      environment.
- [ ] A stream test checks the time to first token and the token count within tolerance.
- [ ] The baseline profile is decided against the v0.5.0 NVIDIA run logs (ADR 0012 open
      question 1).

### 5. Refuse a public bind with authentication off (#210)
`security`, `priority:p1` · Depends on: 1
- [ ] The scope is the one in #210, done before the freeze. Tests cover a loopback bind, a
      public bind, and each `APP_ENV`.

### 6. Load scenarios
`load`, `testing`, `priority:p0` · Depends on: 3, 4
- [ ] Locust is a dev dependency, justified in the PR (90-day rule). The scenarios live in
      `loadtest/` and run with `make load`.
- [ ] Four scenarios: a new thread, a follow-up turn, an approval round trip, and a 60/30/10
      mix. Each virtual user has its own Keycloak test user and token.
- [ ] The client parses the SSE events and records time to first token, run duration, and
      status and error code per run. A unit test covers the parser on recorded streams.
- [ ] A step profile raises the run rate in 10-minute steps until an SLO breaks.

### 7. Load baseline
`load`, `priority:p0` · Depends on: 6
- [ ] One run of every scenario on the reference stack with the agreed profile.
- [ ] `docs/releases/v0.9.0-gate/load-baseline.json` records, per scenario: the highest
      sustained runs per second within the SLOs, the knee, and the failure mode one step past
      it. It also records the image digest, host description and fake-model profile.
- [ ] A comparison script reports a regression of more than 10% against the baseline on the
      same host and profile. A test covers it on fixture files.
- [ ] Each bottleneck found becomes its own issue. None is fixed here.

### 8. Threat model
`security`, `documentation`, `priority:p0` · Depends on: 1
- [ ] `docs/security/threat-model.md` maps each entry of the OWASP Top 10 for LLM
      Applications 2026 and the OWASP Top 10 for Agentic Applications to a control, a test,
      or a known issue. The entry text is taken from the OWASP site.
- [ ] It covers memory, approvals and mutating tools (v0.7.0), and the browser and OIDC
      (v0.8.0).
- [ ] Every row without a test is filed as an issue, labelled `v0.9.0` or `deferred:post-1.0`.

### 9. DAST workflow
`security`, `ci`, `priority:p1` · Depends on: 3
- [ ] A `workflow_dispatch` workflow starts the reference stack and authenticates as a test
      user. It runs ZAP's API scan, pinned by SHA, against `/openapi.json`.
- [ ] Findings at medium or above fail the run unless a rules file lists them with a reason.
      The report is uploaded as an artifact.
- [ ] One clean run is linked from the release verification.

### 10. Restore drill
`reliability`, `deployment`, `priority:p0` · Depends on: 3
- [ ] `scripts/dr_drill.py` seeds threads, memories and an erasure, and takes a base backup
      with WAL archiving. It writes more data, restores to a recorded point in time on a new
      container, and runs `setup` and the smoke test.
- [ ] The drill replays the erasure per the runbook, checks that the `UNLOGGED` rate-limit
      table is empty, and deletes the restored container.
- [ ] RTO and RPO are printed and recorded. Any runbook step that proved wrong is fixed in
      `OPERATIONS.md`.

### 11. Rollback rehearsal
`reliability`, `deployment`, `priority:p1` · Depends on: 3
- [ ] The v0.9.0 image is deployed with its migrations, then rolled back to the v0.8.0 image
      per the runbook. The smoke test passes on the old image against the migrated database.
- [ ] The result is recorded. If a migration is not backward compatible, that is a blocking
      issue.

### 12. Freeze policy and pre-release tags
`ci`, `documentation`, `priority:p0` · Depends on: 1
- [ ] `CONTRIBUTING.md` states the freeze (ADR 0012 decision 11), and the PR template gains a
      freeze checkbox.
- [ ] `TAG_PATTERN` accepts `vX.Y.Z-rc.N`, and `check-release` requires the base version's
      CHANGELOG section.
- [ ] `deploy.yml` skips the production job for pre-release tags, and its release step marks
      them as pre-releases. Tests are added in `test_deploy_tools.py` and
      `test_deploy_workflow.py`.

### 13. Live evals on NVIDIA
`evaluation`, `priority:p0` · Depends on: 1
- [ ] One `--trials 3` run of the regression and security suites on the NVIDIA development
      model, committed as the v0.9.0 baseline.
- [ ] `compare` is run against the latest committed baseline. The result is recorded as it
      is, with the owner's sign-off if it is failing or inconclusive.
- [ ] The cause of the 2026-10-28 nightly failure is found and either fixed or recorded.

### 14. Docs and operations
`documentation`, `priority:p1` · Depends on: 7, 10
- [ ] `OPERATIONS.md` gains a "Capacity" section with the baseline, its host and profile, and
      the caveat that it is not hosted capacity. The DR section gains the drill's RTO and RPO.
- [ ] `docs/ROADMAP.md`, `CLAUDE.md` and `README.md` describe v0.9.0 and the freeze.

### 15. v0.9.0 release gate
`testing`, `priority:p0` · Depends on: all core
- [ ] All core issues are closed, and `make format lint typecheck test security` and the
      `web-*` gates pass.
- [ ] The load baseline, the clean DAST run, the restore drill, the rollback rehearsal and
      the live eval are each linked with evidence.
- [ ] `docs/releases/v0.9.0-release-verification.md` lists the deferred gates as known
      issues, and states that no hosted deployment has run.
- [ ] Version 0.9.0, the CHANGELOG and the token usage report are committed. Nothing is
      tagged without the owner, and the freeze starts at the tag.
