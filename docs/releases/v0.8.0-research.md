# v0.8.0 research: User Application

Status: research for the owner, not a decision. Collected 2026-10-28. Input to a future ADR 0010.
Roadmap line: "v0.8.0 User Application: Web UX + chat experience". Nothing else is defined yet.

Web claims below come from search excerpts only; the vendor pages themselves were not read.
Treat versions and feature claims as perishable and re-check before the ADR.

## 1. What the backend already gives a UI (v0.7.0 on `main`)

| UI need | Existing API | Gap |
| --- | --- | --- |
| Send a message, stream the answer | `POST /v1/agent/stream` (SSE: `run_started`, `token`, `tool_call`, `final`, `approval_required`, `error`, `done`; protocol version 1) | None. Browsers must use `fetch`, not `EventSource` (needs a body and `Authorization`); README has a reader. |
| Approve or reject a tool call | `POST /v1/threads/{id}/approvals/{approval_id}` and `.../stream` | None. |
| Resume a conversation | `GET /v1/threads/{id}/messages` (paged, user/assistant turns) | No tool-call or approval history in the replay. |
| Conversation list | `GET /v1/me/threads` (ids and metadata, deliberately no content) | **No title or preview**, so a sidebar has nothing to show. |
| Memories (view, delete) | `GET/DELETE /v1/me/memories` | No create or edit from the UI (the model writes them after approval). |
| Export and erase | `GET /v1/me/export`, `DELETE /v1/me/threads`, `DELETE /v1/me/memories` | None. |
| Auth | Bearer JWT only; CORS is exact-origin, bearer-only, never cookies | **No login flow.** The API verifies tokens; something else must obtain them. |
| Feedback | none | Issue #104 (thumbs up/down per run), deferred here from v0.5.0 (ADR 0007 section 7). |
| Stop generation | cancelling the fetch closes the stream and cancels the run | No explicit cancel endpoint; fine for a first UI. |

Constraint from `CLAUDE.md`: no new persistence, queues or retrieval without a product requirement and an ADR. A
conversation title is a small piece of new state, so it needs an ADR decision (section 4, Q3).

## 2. Decisions the UI forces

### 2.1 Where the UI lives and how it is served

| Option | For | Against |
| --- | --- | --- |
| A. Separate static SPA (own build, own origin), calls the API with CORS | Clean boundary; API stays JSON/SSE only; CORS and bearer design already exist | A second deploy target and build chain; node toolchain enters CI |
| B. SPA bundled into the image and served by FastAPI | One deploy, same origin, no CORS | Couples release cadence; widens the attack surface of the API container; static serving and CSP in the API app |
| C. Server-rendered pages (HTMX/Jinja) from FastAPI | No node, no JS build, tiny supply chain | Weak fit for token streaming plus approval cards; the repo's SSE shape is JSON events, not HTML fragments |

Recommendation: **A**, in a new top-level `web/` directory (monorepo, so the SSE contract and the UI change in one PR).
It keeps production and staging out of scope (nothing deploys until after v1.0.0) because the UI is verified locally.

### 2.2 Stack and chat component layer

| Option | Notes |
| --- | --- |
| Hand-written React + Vite + TypeScript against our own SSE events | Fewest dependencies and no protocol translation; the stream contract is small (7 events). Most code to write (message list, markdown, scroll, approval card). |
| [assistant-ui](https://www.assistant-ui.com/docs/runtimes/ai-sdk/overview) | Backend-agnostic React chat primitives; supports custom runtimes. Adds a dependency tree. |
| Vercel AI SDK `useChat` ([stream protocol](https://ai-sdk.dev/docs/ai-sdk-ui/stream-protocol)) | A custom backend must emit its SSE parts and set `x-vercel-ai-ui-message-stream: v1`. That means a translating endpoint in our API and tracking a fast-moving protocol (search results span v4 to v7). Tool-approval parts were not confirmed. |
| [AG-UI](https://docs.ag-ui.com/sdk/python/core/events) (CopilotKit's agent-UI protocol) | Event set maps well (`RUN_STARTED`, `TEXT_MESSAGE_*`, `TOOL_CALL_*`, `RUN_FINISHED`, `RUN_ERROR`) and has a Python SDK. Interrupt/approval support was **not confirmed** in the results. Adds a protocol and a vendor ecosystem. |
| LangGraph SDK `useStream` ([reference](https://reference.langchain.com/javascript/langchain-react/interrupts)) | First-class interrupts (`interrupt`, `respond`) but speaks the Agent Server protocol, which this API deliberately is not (ADR 0005, 0006). Would mean exposing the Agent Server, which has its own auth and known limits. |

Recommendation: **React + Vite + TypeScript, own thin client over our SSE contract**, optionally headless primitives
only. Reasons: the contract already exists and is versioned; every protocol adapter above adds a translation layer on
the security-sensitive path (approvals) and a dependency that must pass the 90-day `new-dependencies` rule. Revisit
assistant-ui if the hand-written message list becomes the largest cost. This is a judgement, not a measured result.

### 2.3 Authentication in the browser (the hardest question)

The API accepts only a bearer JWT from the configured issuer. A browser app needs a way to get one.

- Current guidance ([OAuth 2.0 for Browser-Based Apps](https://datatracker.ietf.org/doc/rfc10017/); its status was unclear in the
  results, so check the datatracker): Authorization Code with PKCE; the choices are a backend-for-frontend (BFF) that holds
  tokens server-side, a token-mediating backend, or a browser-only OAuth client holding the access token in memory.
- Our API is bearer-only and CORS never allows cookies. A BFF using cookies would contradict that design and need CSRF
  controls. A browser-only PKCE client matches the existing API with no backend change.
- Development: `make dev-token` mints tokens for a local JWKS; the UI can use a dev-only token box. Real IdP login (which
  provider, audiences) is the same open question as ADR 0008 Q2 and is not decided.

Recommendation: **browser-only Authorization Code + PKCE against the owner's IdP, access token in memory only (never
`localStorage`), short lifetimes, silent refresh via a refresh-token policy the IdP supports**; a dev-only login that uses
`make dev-token` for local work. Needs an owner decision on the IdP (Q1).

### 2.4 Rendering untrusted model output

Model text is untrusted (SECURITY.md). A chat UI is where prompt injection becomes XSS or data exfiltration:

- Render markdown with a sanitising renderer; no raw HTML; links `rel="noopener noreferrer"`; images off by default
  (an image URL in model output is a classic exfiltration channel); code blocks as text.
- Strict CSP on the host (no inline script, `connect-src` limited to the API origin).
- The approval card must show the **server-provided** tool name and arguments, not model prose, and must be a separate
  non-model-styled component, so injected text cannot imitate an approval prompt.
- A UI security test set: XSS payloads in `final` and `token`, markdown image beacons, look-alike approval text.

### 2.5 Streaming mechanics

- `fetch` + `ReadableStream` SSE parser, `AbortController` for Stop, reconnect is **not** resume (a run is not
  resumable), so show the partial answer and offer retry; history comes from `GET .../messages`.
- Handle `error` then `done`, `approval_required` ending a stream, and `429`/`409 thread_busy` before the first byte
  with `Retry-After`.
- Token deltas are a preview; `final` is authoritative (documented in `streaming.py`), so the UI replaces preview with
  `final`.

### 2.6 Feedback (#104)

Scope is already written in issue #104: score -1/1, enum reason, no free text, `feedback:write` scope, idempotent per
(owner, run), telemetry event. It needs a stable `run_id` on `run_started`/`final` (check it exists; if not, that is an
additive protocol change, `STREAM_PROTOCOL_VERSION` stays 1 for additive fields).

## 3. Proposed scope for v0.8.0 (for the owner to cut)

Core (p0):
1. ADR 0010: User application (decisions in section 2; accepts the open questions).
2. Backend gaps: thread title/preview in `GET /v1/me/threads` (or a title set from the first user turn, stored how?),
   `run_id` on the stream, tool-call and approval history in the messages replay.
3. `web/` scaffold: Vite + React + TS, lint, typecheck, unit tests, CI job (node pinned by digest), dependency review.
4. SSE client with fake-server tests (all seven events, error mid-stream, abort, 409/429).
5. Chat screen: send, stream, stop, retry, markdown (sanitised), error states.
6. Conversation list and resume; delete a conversation.
7. Approval card wired to the approval API (approve/reject, stream the continuation).
8. Browser auth (PKCE or dev-token), in-memory token.
9. UI security tests (section 2.4) and a CSP.
10. v0.8.0 release gate: gates, end-to-end local run on the NVIDIA dev model or the fake model, accessibility pass.

Should have (p1): memories panel (list/delete) and data-rights page (export/erase); feedback (#104); dark mode;
keyboard and screen-reader basics (WCAG 2.2 AA check on the chat and approval flows); mobile layout.

Deferred: multi-modal input/file upload (needs an upload threat model), voice, sharing links, multi-user threads, i18n,
a hosted deployment of the UI (after v1.0.0, like everything else), calibrated judges (#103).

Size: roughly 12 to 15 PRs if each stays under 400 changed lines; the frontend is a new language in the repo, so the
first scaffold PR will be large unless split into tooling, then code.

## 4. Open questions for the owner

1. **IdP.** Which identity provider, and is a dev-token-only UI acceptable for v0.8.0 (real login deferred with
   deployment)? This decides the size of the auth work.
2. **Product shape.** Single-page personal assistant only (matches v0.7.0's memory requirement), or anything more (agents
   picker, settings, workspaces)? Recommendation: assistant only.
3. **Conversation titles.** New state is needed (title column or a store item). Options: derive from the first user message
   client-side only (no backend state, but not available on another device), or store a short server-side title via the
   existing memory/store path under an ADR. Recommendation: store a bounded title, owner-keyed, covered by data-rights.
4. **Stack.** Accept React + Vite + TS with own SSE client (recommended), or prefer a library (assistant-ui)?
5. **Hosting.** Separate static host (A), or served from the API image (B)? Recommendation A; nothing is deployed anyway.
6. **Node in the repo.** OK to add a Node toolchain, lockfile and CI job? It changes `Dockerfile`/CI scope and the supply
   chain (npm audit, the 90-day dependency rule).
7. **Feedback in or out** of v0.8.0 (issue #104)?
8. **Accessibility target** (WCAG 2.2 AA is the proposal) and supported browsers.

## 5. Risks

- Prompt-injection-to-XSS or exfiltration through rendered output (section 2.4); the main new attack surface.
- Browser token handling; a mistake here undoes the v0.4.0 identity model.
- npm supply chain; the frontend dependency tree is far larger than the Python one.
- Approval spoofing in the UI.
- Scope creep: a UI invites features. Keep to the cut above.
- Verification: no deployed environment and (until the key is replaced) only fake-model or NVIDIA dev runs, so UX claims
  rest on local runs only; say so in the release record, as for v0.6.0 and v0.7.0.
