Treat versions and feature claims as perishable and re-check before the ADR.

## 1. The constraint that shapes everything

The roadmap theme assumes a running production system: load against it, attack it, restore it, freeze it.
The owner decided on 2026-10-27 that production deployment is "not exercised or tested until after v1.0.0"
(ADR 0009, ADR 0010), and on 2026-10-28 deferred #285, #290 and #293 to the same point. Read literally,
v0.9.0 has no system to test and v1.0.0 ("Stable production platform") ships without ever having run in
production.

So the first question is not which load tool to use but **what environment v0.9.0 certifies** (section 4, Q1):

| Option | What "production candidate" means | Cost |
| --- | --- | --- |
| A. Local reference stack | `docker-compose.yml` (Postgres, API, Keycloak) plus `web/`, built from the published image digest, is the system under test. Load, DAST and restore drills all run against it. | No account or spend. Numbers describe a laptop, not Render; RTO/RPO of Render PITR stay unknown. |
| B. Lift the deferral for staging only | Render staging (ADR 0008) is stood up; production stays off until after v1.0.0. | Render spend and the owner pre-actions in v0.6.0 gate row 3. Closes most of #150, #151, #154, #156. |
| C. Lift the deferral fully | v0.9.0 is the v0.6.0 gate (#160) finally run, plus load and DR. | Largest; also needs a funded provider key for meaningful SLO checks. |

Recommendation: **A, with B as an explicit owner choice.** A is consistent with every decision since
v0.7.0 and still produces real, repeatable artefacts (scripts, thresholds, drills) that B or C can re-run
later against Render unchanged. Whatever is chosen, the release record must say which environment the
numbers come from.

## 3. Decisions the theme forces

### 3.1 Load testing

| Tool | For | Against |
| --- | --- | --- |
| k6 | Strong for CI thresholds; JS scripts | AGPL-3.0; SSE support is disputed in the sources (extension vs native), TTFT needs custom metrics; adds a JS toolchain beside `web/` |
| Locust | Python, same language as the repo; easy to parse our JSON SSE events | Reported GIL limits for streaming-heavy load (an LLM-Locust extension exists) |
| LLM benchmarks (GenAI-Perf, llmperf, guidellm) | Token-level metrics | Measure a model server, not an authenticated agent API with threads and approvals |

Recommendation: **Locust**, scripted against `POST /v1/agent/stream` with real JWTs from the local Keycloak,
plus a **fake model with configurable latency and token rate** (a small change in `models/factory.py`,
dev/test only) so the test exercises streaming, checkpoints, leases and limits without a provider. Record
three numbers per scenario: max sustained runs/s within SLO, the knee, and the failure mode past it.
Provider latency is out of scope unless a funded key exists.

### 3.2 Security

- **Threat model refresh** against the OWASP Top 10 for LLM Applications 2026 (released August 2026) and the
  OWASP Top 10 for Agentic Applications (December 2025). Map each item to code, test or known issue.
- **DAST** with ZAP's API scan (`zaproxy/action-api-scan`) against the OpenAPI document of the local stack,
  authenticated. Pin the action by SHA like every other action here.
- **Browser checks deferred in #290** (CSP, redirect, silent renew) are the only security items in the
  v0.8.0 deferral that a local stack can close. Proposed for v0.9.0 even under option A.
- An **external pentest** needs a deployed target and budget; out of scope under option A.

### 3.3 Disaster recovery

Under option A: a scripted drill on the compose Postgres (`pg_dump`/restore and a WAL-based point-in-time
restore), then `setup`, the smoke test and the erasure replay from the restore runbook; record RTO and
RPO for that setup. Also rehearse the rollback runbook (previous digest plus a down-migration check).
Under B or C the same drill runs once on Render, filling the blanks in `OPERATIONS.md`.

### 3.4 Release freeze

Proposed meaning: after the v0.9.0 tag, `main` takes only fixes, docs and security updates until v1.0.0;
the public API (`/v1`), SSE protocol version 1, settings names and migrations are frozen, and anything
breaking needs an owner exception. Ship `v1.0.0-rc.N` tags from `main`. `check-release` and the tag
ruleset may need to accept pre-release tags; that is a test-covered change in `scripts/deploy_tools.py`.

## 4. Open questions for the owner

1. **Environment** (section 1): local reference stack (A), Render staging (B), or full production (C)?
2. **Debt**: close, or formally re-defer to "after v1.0.0", each of #160, #253, #293 and their open children?
   Under A most of #150, #151, #154, #156 stay deferred.
3. **Provider key**: will a working NVIDIA key (or a funded OpenAI key) exist for v0.9.0? Without one, every
   SLO and security number comes from fakes.
4. **Load targets**: what concurrent users and runs/s should the candidate support? Without a number the test
   can only report a knee, not pass or fail.
5. **Fake-latency model**: accept a dev/test-only latency option in the fake model?
6. **Security scope**: threat model, DAST and #290 in v0.9.0; external pentest after v1.0.0?
7. **Freeze**: accept the definition in 3.4, and `-rc.N` tags before v1.0.0?
8. **Old issues**: #103 (LLM judge), #162 (token report), #210 (public bind with auth off): in, or after v1.0.0?

## 5. Risks

- Certifying a laptop: option A numbers can be mistaken for production capacity. The release notes must say so.
- Three earlier gates stayed open; a fourth "production candidate" with open gates weakens the label.
- No working model key means the eval and security gates stay inconclusive, as in v0.6.0 to v0.8.0.
- A freeze without the deferred production work means v1.0.0 changes infrastructure after the freeze.
