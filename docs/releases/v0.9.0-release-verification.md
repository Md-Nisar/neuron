# v0.9.0 release verification (#337)

Release gate record for v0.9.0 "Production Candidate" (ADR 0012). Everything ran on the **local
reference stack** (`docker-compose.reference.yml`: two API replicas, Postgres 16, Keycloak 26, the
fake model with latency) on one 4-CPU Linux host, plus the NVIDIA development model for the live
eval. **No hosted deployment (Render), real browser, production model or external penetration
test was used.** The gates #160 (v0.6.0), #253 (v0.7.0) and #293 (v0.8.0) are deferred until after
v1.0.0 and labelled `deferred:post-1.0`; they are not closed. Nothing is tagged; the freeze starts
at the tag.

## Load baseline (#329)

Reference stack, fake model: 800 ms to first token, 40 tokens/s, 200 tokens; 300 Keycloak test
users; 6 s think time. **Steps of 90 s and 30 more users each**, not the 10 minutes the issue named.
SLOs: time to first token p90 at most 15 s, run duration p95 at most 30 s, at most 0.5% failed runs.

| Scenario | Highest sustained runs/s inside the SLOs | At users | First SLO breach |
| --- | --- | --- | --- |
| new thread | 12.5 | 120 | 210 users: availability |
| follow-up turn | 11.2 | 150 | 210 users: availability |
| approval round trip | 15.9 | 90 | 210 users: availability |
| 60/30/10 mix | 12.4 | 150 | 210 users: availability |

- **Failure mode one step past the knee:** `503 too_many_streams` from the replicas
  (`APP_MAX_CONCURRENT_STREAMS`, default 100 per process, so 200 across two), 5 to 8% of runs at 240
  users. Latency rose steadily before that (time to first token p90 1.3 s at 30 users, 7 to 12 s at
  180 to 210) while throughput flattened near 12 runs/s for most scenarios.
- **A first attempt was invalid:** with the default per-user token budget (100,000 an hour) the load
  users hit `429 quota_exceeded` within minutes, so the run rate measured the budget. The reference
  stack raises it (`APP_USER_TOKEN_BUDGET`) and says so; that attempt is not recorded.
- **Not shown:** which resource saturates. CPU, Postgres and pool metrics were not recorded, and
  the load generator shared the host. Capacity planning needs that before the numbers mean more
  than "this laptop-class host, this profile".
- **Profile caveat:** ADR 0012's accepted profile is far faster than the NVIDIA model, so concurrent
  streams are fewer than a real model would hold at the same request rate. The next section repeats
  the run with real-model latency.

### Same run with real-model latency

Fake model at 2000 ms to first token, 10 tokens/s, 75 tokens (about 10 s a run). Six direct streaming
calls to `nemotron-3-ultra-550b-a55b` on 2026-10-28 gave a first token after 0.9 to 16 s (usually
1.4 to 2 s) and a 150-word answer in 3.5 to 25 s, then a `429`; six samples, a rough profile only.
Everything else as above. Files: `load-baseline-real-latency.json`, `load-steps-real-latency/`.

| Scenario | Highest sustained runs/s inside the SLOs | At users | First SLO breach |
| --- | --- | --- | --- |
| new thread | 16.9 | 180 | 210 users: availability |
| follow-up turn | 15.6 | 180 | 210 users: availability |
| approval round trip | 21.6 | 180 | 210 users: availability |
| 60/30/10 mix | 16.1 | 180 | 210 users: availability |

- **Same limit, now explained:** every scenario first fails at 210 users with `503 too_many_streams`,
  while time to first token p90 (3.7 to 5.7 s) and run p95 (12 to 16 s) are still well inside the
  SLOs. With runs of about 10 s, 200 stream slots (100 per replica) carry about 20 runs/s, which is
  where the rate stops. The first thing to raise is `APP_MAX_CONCURRENT_STREAMS` (#339).
- **The runs/s are partly set by the load itself:** users wait 6 s between runs, so the rate follows
  the user count until a limit is hit. The numbers say where the first limit is, not how much more
  the stack could carry.
- **The real model was not load tested.** The free NVIDIA key allows 40 requests per minute (about
  0.67 runs/s), so a run against it would measure the key. Real-model results may differ in either
  direction, since its latency varies widely.

## Restore drill (#332)

`scripts/dr_drill.py` (OPERATIONS.md, "Backups and restore"). Seeded users, took a base backup with
WAL archiving, wrote more, recorded a point in time T, erased one user's data after T, restored to T
in a new container, ran `setup` as the migrator, started a throwaway replica and ran the smoke test.

- **RTO:** database usable 6.2 s after the restore started; replica serving and smoke test passed
  22.5 s after (a small database; the base backup was copied from a container on the same host).
- **RPO to T:** the newest restored thread is 2 s before T; data after T is lost by choice. The
  archive bound is `archive_timeout` (10 s).
- **Erasure replay:** the erased user's 3 threads were back after the restore and gone after the
  replay (`DELETE /v1/me/threads`), as OPERATIONS.md says.
- **`UNLOGGED` rate-limit table:** 0 rows after the restore (2 on the source), as documented.
- **Deleted:** the restored database and the staging replica were removed at the end.
- **Fixes found:** the archived WAL files must be readable by the restoring container; segments from
  before the backup are not needed (a load run leaves hundreds of 16 MB files).
- **Not shown:** a restore on Render; sizes beyond a few hundred threads; encrypted backups.

## Rollback rehearsal (#333)

`scripts/rollback_rehearsal.sh`: deployed the v0.9.0 image (migrations 1 to 16), created a thread,
redeployed the v0.8.0 image (its `setup` ran over the same database; migrations unchanged), both
replicas ready, smoke tests passed, the thread was readable through the other replica, then rolled
forward. v0.9.0 adds no migration, so this proves the procedure and the old image's tolerance of the
current schema, not an expand/contract case.

## DAST (#331)

ZAP API scan (image pinned by digest) of `/openapi.json` on the reference stack, signed in as a test
user: 113 rules passed, 0 failed, 1 warning (`SQL Injection` on `/v1/me/threads?limit=`). By hand,
every payload on `limit` returns `422`; ZAP compared a `200` with a rate-limited `429`. Excused with
that reason in `deploy/reference/zap-rules.tsv`. The scan covered only the 26 URLs of the OpenAPI
document, rate limited, as one user.

## Live eval (#335)

`neuron-eval --trials 3` on `nemotron-3-ultra-550b-a55b` (`APP_ENV=development`).

| Suite | Cases | Pass rate | pass^k |
| --- | --- | --- | --- |
| single_turn | 16 | 0.74 | 0.64 |
| multi_turn | 13 | 1.00 | n/a |
| security | 31 | 1.00 | 1.00 |
| approval | 13 | 1.00 | n/a |

`compare` against the committed `nemotron-3-super-120b-a12b` baseline: **regression**.
`calculator-tool-selection-001`, `utc-tool-selection-001` and `-002` passed 3/3 there and fail 3/3
here (the model answers without calling the tool); 57 trials were infrastructure errors (rate
limits), so the run is also inconclusive. The owner decided (2026-10-28) to keep the super-120b baseline; the ultra
report is kept as evidence in `eval-report-ultra-550b.json`, not as a baseline, so the nightly (on
ultra) applies only the security gate. **The cause of the 2026-10-28 nightly failure:** the report
schema listed three suites and `neuron-eval` also runs `approval`, so `compare` rejected the report.
Fixed in `tests/fixtures/eval_report.schema.json`, with a test. The model switch to ultra (#229) had
already fixed the earlier `404` for `nemotron-3-super-120b-a12b`.
