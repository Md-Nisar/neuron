## 9. Eval harness v2: repeated trials, pass^k, intervals, trajectory, robust graders

**Labels:** `evaluation`, `testing`, `priority:p0`, `v0.5.0` · **Depends on:** 1

Acceptance criteria:
- [ ] `neuron-eval --trials k` (default 1) runs each case k times; the report gives
      per case: passes out of k; per category and suite: pass rate, pass^k and a 95%
      Wilson interval.
- [ ] Trajectory matching per case: `unordered` (default) or `subset`; every case
      also asserts no tool outside the caller's permissions ran.
- [ ] Less wording-sensitive grading. 26 of the 29 single- and multi-turn cases are
      judged by keywords (e.g. `ambiguous-request-001` fails on phrasing). Cases
      gain structured expectations where the answer allows it (a number within a
      tolerance, a refusal flag, a clarification flag in `AgentAnswer`), and keyword
      lists are widened or replaced; each changed case records why.
- [ ] Report schema is versioned (`report_version`) and adds latency p50/p95,
      tokens by kind (and estimated cost if #6's optional part landed), model, git
      SHA and dataset versions; a JSON Schema file under `tests/fixtures` validates it.
- [ ] Run failures are classified: infrastructure (provider, quota, timeout,
      configuration) vs quality; infrastructure errors are reported separately and
      never counted as quality passes.
- [ ] `--suite`, `--category` and `--output <file>` options; stdout stays JSON.
- [ ] `python -m neuron_agent.evaluation` runs the CLI (today it does nothing).
- [ ] Fake-model tests cover k>1 aggregation, interval maths and classification.
- [ ] `EVALUATION.md` documents the metrics and how to read them.

## 10. Eval baselines, regression comparison and the live-eval workflow

**Labels:** `evaluation`, `testing`, `priority:p0`, `v0.5.0` · **Depends on:** 3, 9

At current dataset sizes a suite-level interval cannot catch real regressions: 16
cases × 3 trials at about 0.8 gives a 95% Wilson interval of roughly 0.67–0.89, so
losing two whole cases still looks like noise (multi-turn, 13 cases, is worse).
The gate is therefore **per case**; suite intervals are reported, not gated, until a
gated suite reaches about 50 cases.

Acceptance criteria:
- [ ] `neuron-eval compare <baseline> <candidate>` exits non-zero when:
  - a regression-suite case that passed every trial in the baseline fails every
    trial in the candidate; or
  - any security-suite case fails any trial (pass^k = 100%).
- [ ] `compare` also prints per-suite and per-category pass rates with 95% Wilson
      intervals and deltas, as information only; infrastructure errors are listed
      separately and never trigger the gate (they fail the run as "inconclusive").
- [ ] Tests cover a per-case flip, a one-trial wobble (not gated), a security
      failure and an infrastructure-only failure.
- [ ] `evals/baselines/<model>.json` committed for the development baseline model
      (`nvidia/nemotron-3-super-120b-a12b`), from a live run with `--trials 3`.
- [ ] A nightly and manually-triggered workflow runs the live suites when the
      provider secret is configured, skips cleanly when it is not, runs `compare`
      against the committed baseline, and uploads the report artifact. Its timeout
      allows about an hour (3 trials × ~20 minutes).
- [ ] The NVIDIA free tier's rate limits and terms for automated CI runs are
      confirmed and recorded in `EVALUATION.md`; the workflow throttles to them.
- [ ] With `APP_ENABLE_LANGSMITH`, results are also uploaded as a LangSmith
      experiment (optional, off by default).
- [ ] Workflow uses least-privilege permissions and never prints secrets.
- [ ] `EVALUATION.md` documents how to refresh a baseline and who approves it.

## 18. Bug: a tool input error aborts the run instead of letting the model recover

**Labels:** `reliability`, `priority:p0`, `v0.5.0` · **Depends on:** none

Found by the live baseline (`adversarial-tool-abuse-002`): invalid calculator input
raises `ValidationAppError`, which aborts the whole run with `validation_error`
instead of returning a tool error the model can act on.

Acceptance criteria:
- [ ] A tool's input-validation failure becomes a tool error message returned to the
      model (no input echoed beyond what the tool contract allows); the run
      continues and can answer or refuse.
- [ ] Authorization denials and timeouts keep their current behaviour (ADR 0003).
- [ ] The tool failure is still logged (`tool_call_failed`) and counted.
- [ ] Fake-model test reproduces the abort first, then passes;
      `adversarial-tool-abuse-002` passes live.

## 19. Bug: multi-step tool use hits the 5-iteration limit

**Labels:** `reliability`, `evaluation`, `priority:p1`, `v0.5.0` · **Depends on:** none

Found by the live baseline (`tool-use-across-turns-002`): the run hits the agent's
5-iteration limit and fails with `agent_execution_error`.

Acceptance criteria:
- [ ] Root cause recorded: whether the limit is too low for legitimate multi-step
      use, or the model loops (e.g. repeated identical tool calls).
- [ ] The fix is the smaller of: a configurable limit with a justified default, or
      loop detection; reaching the limit returns a classified, user-visible error.
- [ ] Fake-model test covers the limit and the chosen fix;
      `tool-use-across-turns-002` passes live.

### 12. User feedback endpoint tied to runs (deferred to v0.8.0)

**Labels:** `security`, `state`

Needs a UI to be useful. When picked up:
`POST /v1/threads/{thread_id}/runs/{run_id}/feedback` with `{score: -1 | 1, reason?:
<enum>}`, a `feedback:write` scope, thread ownership with the same `404` for missing
and foreign threads, recorded as a log event, span event and metric, and forwarded
to LangSmith feedback when enabled.
