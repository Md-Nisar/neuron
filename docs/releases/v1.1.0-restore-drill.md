# v1.1.0 restore drill with knowledge

RAG-07.03 (#518): the restore drill (`scripts/dr_drill.py`, first run in v0.9.0) now covers
knowledge data and the blob store. Run on 2026-11-10 on the local reference stack
(`docker-compose.reference.yml`, `KNOWLEDGE_ENABLED=true`, the worker started with `--no-deps`, no
docling-serve). The image was built from this branch. Raw output: `v1.1.0-gate/restore-drill.json`.

## Method

The v0.9.0 steps are unchanged: seed users, take a base backup with WAL archiving, write more,
record a point in time T, erase one user's threads after T, restore to T in a new container, run
`setup`, start a throwaway replica and run the smoke test, then replay the erasure.

Added for knowledge:

1. **Before the backup.** One user creates a base and uploads two Markdown files: the known
   document (the smoke test's synthetic text) and a second one. The worker ingests both with the
   fake embedding provider. The known question cites the known document on the source stack.
2. **After T.** The user uploads a third file and deletes the second; the drill waits until the
   purge has removed its row and file. Then the blob volume is copied. This is the file backup,
   from a later moment than the database's T.
3. **After the restore.** Before any worker runs, `neuron-worker check-blobs` runs against the
   restored database and the copied files. The staging replica mounts the same copy and answers
   the known question (`search: Skerryvore lighthouse keeper`, a scripted fake-model search
   scoped to the base).

The drill passes only if the known document is cited, `check-blobs` exits 1, `missing_blobs` is
exactly the document deleted after T, and at least one orphan file is counted.

## Fixes found by the drill

- **The drill restored into `postgres:16`, which has no pgvector.** The reference stack's
  database has used `pgvector/pgvector:pg16` since RAG-01.01, so a restore of the knowledge
  tables could not have started. The drill now uses the reference stack's image, pinned by digest.
- **The reference stack could not run knowledge without a provider key.** Its embedding provider
  defaulted to `nvidia`, and its role permissions lacked the knowledge tools. It now uses the fake
  embedding provider (`KNOWLEDGE_EMBEDDING_PROVIDER` overrides it) and grants
  `tools:search_knowledge`, `tools:list_knowledge_bases` and `tools:get_document_excerpt`, as the
  local stack does.
- **No way to check files against rows after a restore.** The runbook said to keep the worker
  stopped until the store and the database match, but gave no way to check that. The new
  `neuron-worker check-blobs` does, and is now step 4 of "Backups and restore" in OPERATIONS.md.

## Not shown

- **Memories.** With knowledge on, a run's first model call must search
  (`knowledge_first_middleware`, RAG-08.01). The fake model's scripted `remember:` turn then
  ends as a plain thread, so this run seeded no memories (`memories_seeded: 0`). The v0.9.0 run
  covered them, and neither run checked them after the restore.
- **An S3 bucket.** The drill copies a local volume; restoring a bucket version is the
  operator's.
- **A restore on Render**, and sizes beyond a few documents.
- **The blob sweep deleting the orphan.** Its grace period is at least an hour. The deletion
  itself is tested in `tests/integration/test_postgres_knowledge_reconcile.py`.
