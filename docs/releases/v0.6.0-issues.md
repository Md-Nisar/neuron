- The image's `CMD` becomes `["neuron-api"]`.

Acceptance criteria:
- [ ] No `os.getenv`/`os.environ` read remains in `api/` (a test greps `src/` for env
      reads outside `config/settings.py` and the documented
      `observability/langsmith_governance.py` exception; it fails on today's
      `api/main.py:600-601`).
- [ ] A unit test asserts the Uvicorn config built by `main()`: host, port, graceful
      timeout derived from `APP_RUN_TIMEOUT_SECONDS`, `workers` unset, and the chosen
      proxy-header setting.
- [ ] With the chosen proxy handling, a request through a trusted proxy is keyed by
      the forwarded client address and one through an untrusted peer by the peer

- [ ] ADR 0004 "v0.4.0 Resource Limits" and `OPERATIONS.md:468` describe the single

## 4. Graceful shutdown for `invoke`: readiness turns 503 and runs drain

**Labels:** `reliability`, `streaming`, `priority:p0`, `v0.6.0` · **Depends on:** 3

Streams already end with `service_shutting_down` within 2 s
(`api/main.py:101`, `_STREAM_SHUTDOWN_GRACE_SECONDS`). `/v1/agent/invoke` runs get no
shutdown signal and are bounded only by `APP_RUN_TIMEOUT_SECONDS=120`, and
`/health/ready` (`api/main.py:357-361`) keeps answering `200` while the process
drains, so a platform can keep routing to an instance that is stopping.

Scope:
- On SIGTERM, before Uvicorn stops, the service enters a draining state:
  `/health/ready` returns `503`; new `/v1/agent/*` runs get `503
  service_shutting_down` with `Retry-After`; in-flight runs continue.
- Logged once: `service_draining` with the number of in-flight runs.

Acceptance criteria:
- [ ] Test: with a run in flight, triggering the drain makes `/health/ready` return
      `503`, refuses a new invoke with `503 service_shutting_down`, and lets the
      in-flight invoke return its `200` answer (fake model with a delay). It fails on
      `main` today.
- [ ] Test: a run still in flight when the graceful timeout ends is cancelled and
      releases its lease (no leaked `thread_busy` or per-user slot).
- [ ] Stream shutdown behaviour is unchanged (existing tests pass).
- [ ] `OPERATIONS.md` documents the shutdown sequence and that the platform grace
      must exceed `APP_RUN_TIMEOUT_SECONDS + 10` (Render
      `maxShutdownDelaySeconds: 150`).

## 5. Enforce the request-body limit on chunked bodies

**Labels:** `security`, `reliability`, `priority:p1`, `v0.6.0` · **Depends on:** none

`limit_request_body_size` (`api/main.py:126-139`) checks only the `Content-Length`
header. A request sent with `Transfer-Encoding: chunked` has none, so its body is read
in full regardless of `APP_MAX_REQUEST_BODY_BYTES`.

Acceptance criteria:
- [ ] A chunked request whose body exceeds `APP_MAX_REQUEST_BODY_BYTES` gets `413
      payload_too_large` and logs `agent_request_body_too_large` without the body
      (test fails before the change).
- [ ] A chunked request within the limit, and requests with `Content-Length`, behave
      as before; a declared length that understates the real body is also cut off at
      the limit.
- [ ] Streaming responses are unaffected (only the request body is counted).
- [ ] `OPERATIONS.md` "Common Failures" row for `413` says the limit applies with or
      without `Content-Length`.

## 10. Versioned schema migrations as a deploy step

**Labels:** `state`, `deployment`, `reliability`, `priority:p0`, `v0.6.0` · **Depends on:** 1, 9

Schema setup is LangGraph's `setup()` plus `neuron_checkpoints_owner_idx`
(`persistence/checkpointer.py:39`, `CREATE INDEX CONCURRENTLY IF NOT EXISTS`), run by
`make db-setup` or at start-up. There is no record of neuron's own schema versions,
and a failed concurrent build leaves an `INVALID` index that `IF NOT EXISTS` then
skips silently. The runtime image has no `make`.

Scope:
- `persistence/migrations.py`: an ordered list of neuron migrations recorded in a
  `neuron_migrations` table, applied by `python -m neuron_agent.persistence.cli setup`
  after LangGraph's `setup()`; concurrent index statements run outside a transaction.
- Optional `APP_POSTGRES_MIGRATION_DSN` (`SecretStr`, never logged), used by `setup`
  when set.
- The existing owner index becomes migration 1.

Acceptance criteria:
- [ ] Postgres tests: `setup` on an empty database applies every migration; a second
      run applies none; a database at migration N gets only the later ones.
- [ ] Postgres test: an `INVALID` `neuron_checkpoints_owner_idx` is detected and
      rebuilt (or `setup` exits non-zero naming it); it is silently skipped on `main`.
- [ ] A test enforces the expand/contract rule: a migration containing `DROP`,
      `RENAME` or `ALTER ... TYPE` fails unless marked as a contract step that names
      the release whose image stopped using the old shape.
- [ ] `setup` exits non-zero on failure, so a Render pre-deploy command cancels the
      deploy.
- [ ] `OPERATIONS.md` "Thread Persistence" documents the migration step, the
      migration DSN and the compatibility rule; ADR 0005 decision 1 is updated to
      point at it.

## 11. Shared run leases: `thread_busy` and per-user concurrent runs across replicas

**Labels:** `state`, `reliability`, `architecture`, `priority:p0`, `v0.6.0` · **Depends on:** 10

`AgentService` keeps `_active_threads`, `_active_thread_owners` and
`_active_runs_by_owner` in process memory (`services/agent_service.py:130-134`,
`_claim` at `:416-478`). Two runs on one thread that land on different replicas both
run and both commit (`OPERATIONS.md:365-369`), and `APP_MAX_CONCURRENT_RUNS_PER_USER`
is multiplied by the replica count.

Scope (ADR 0008 decision 8):
- A run-guard Protocol extracted from `_claim`, with the current in-memory
  implementation and a Postgres one in `persistence/` (lease table, per-owner
  transaction-level advisory lock, `expires_at = now() + APP_RUN_TIMEOUT_SECONDS +
  15 s`, delete on release). No session-level advisory locks.
- `APP_LIMITS_BACKEND` (`auto`/`memory`/`postgres`), shared with drafts 12 and 13.
- `DELETE /v1/threads/{id}` checks the same leases. The stream cap stays per
  process.
- The retention job deletes expired leases. The lease table is an expand-only
  migration.

Acceptance criteria:
- [ ] Postgres integration test with **two app processes** (two Uvicorn servers on
      one database): with `APP_MAX_CONCURRENT_RUNS_PER_USER=1`, a second run for the
      same principal on the other process gets `429 too_many_concurrent_runs`; a
      second run on the same thread gets `409 thread_busy`. It fails with the
      in-memory guard.
- [ ] A lease left by a killed process expires after the run timeout plus 15 s, and
      the thread is usable again.
- [ ] Released leases never leak on success, failure, cancellation, client
      disconnect or stream send timeout (the existing lease tests run against both
      implementations).
- [ ] A guard query failure returns `503 persistence_error` (or the answer to open
      question 7).
- [ ] ADR 0005 decision 5 and Consequences, ADR 0006 Non-goals, `OPERATIONS.md`
      "Scaling" (`:365-369`) and `ARCHITECTURE.md:189` say the guards are shared with
      `APP_LIMITS_BACKEND=postgres`.

## 13. Shared request rate limiting, and a bounded in-memory limiter

**Labels:** `security`, `reliability`, `priority:p0`, `v0.6.0` · **Depends on:** 10, 11

`InMemoryTokenBucketRateLimiter` keeps one bucket per key in a dict that is never
evicted (`security/rate_limiter.py:59`), so failed-authentication IP buckets grow
without bound, and each replica grants the full rate.

Scope:
- `RateLimiter` (`security/rate_limiter.py:22`) becomes async; a Postgres
  implementation on an `UNLOGGED` token-bucket table, one atomic upsert per
  rate-limited request (or the per-process alternative, if open question 7 chooses
  it).
- Keys stored are owner keys or an HMAC of the client IP with a key derived from
  `APP_IDENTITY_HASH_KEY`, never a raw IP.
- The in-memory limiter evicts idle buckets.

Acceptance criteria:
- [ ] Two-process Postgres test: a burst split across both processes is limited to
      `APP_RATE_LIMIT_BURST` in total; it fails with the in-memory limiter.
- [ ] Test: the Postgres table holds no raw IP address after IP-keyed requests.
- [ ] Test: the in-memory limiter's bucket count stays bounded under many distinct
      keys (fails on `main`).
- [ ] The crash trade-off (an `UNLOGGED` table is truncated after a crash, granting a
      burst) is documented in ADR 0004 and `OPERATIONS.md` "Rate Limiting";
      `ARCHITECTURE.md:284` and ADR 0004's Consequences are updated.

## 15. Deploy pipeline: staging by digest, promote the same digest to production

**Labels:** `ci`, `deployment`, `priority:p0`, `v0.6.0` · **Depends on:** 7, 14

There is no deployment workflow and no staging environment. `test_api_contract.py` is a
placeholder that always skips (`CHANGELOG.md:64`), so nothing exercises a deployed
API.

Scope (ADR 0008 decision 6, mechanism per open question 4):
- On a `main` build: verify the digest's attestation, deploy it to staging, wait
  until Render reports it live, run `scripts/smoke_test.py` (`/health/ready`, then one
  authenticated request with the staging service account).
- On a `v*` tag: resolve the digest built for the tagged commit, require that it
  passed staging, deploy it in the `production` Environment (required reviewer),
  smoke-test production, then publish the GitHub Release from the `CHANGELOG.md`
  section.
- Delete the `test_api_contract.py` placeholder; the smoke test replaces it.

Acceptance criteria:
- [ ] Production never rebuilds: a workflow test asserts the production job takes its
      image reference from the staging digest output (`@sha256:` form, never a tag).
- [ ] The production job cannot run without the Environment approval and only on a
      `v*` tag.
- [ ] The smoke test exits non-zero on a non-ready instance or a failed authenticated
      request, and never prints tokens (unit-tested against a local app).
- [ ] A failed smoke test leaves production untouched.
- [ ] A staging deploy of a `main` commit runs end to end (link in the PR).
