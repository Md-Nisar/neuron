## 2. Container image: lockfile-only build, allowlist `.dockerignore`, digest-pinned bases

**Labels:** `deployment`, `security`, `priority:p0`, `v0.6.0` · **Depends on:** 1

`Dockerfile:4` falls back to an unlocked resolve (`uv sync --no-dev --frozen || uv
sync --no-dev`) and `Dockerfile:6` syncs without `--frozen`, so the image can contain
versions `make security` never audited. Both `FROM` lines (`Dockerfile:1`, `:8`) are
tag-pinned. `.dockerignore` excludes only `.env` and `.dev/`, so `.git`, `.venv`,
`.claude/worktrees`, `tests/` and `evals/` enter the build context and the image
(`COPY . .`, then `COPY --from=builder /app /app`). `useradd` (`Dockerfile:13`) picks
whatever UID is free. The v0.3.0 gate could not build the image, and nothing has built
it since.

Scope (ADR 0008 decision 2):
- `uv sync --frozen --no-dev --no-editable`; no fallback. The runtime stage copies
  only `/app/.venv`.
- `.dockerignore` as an allowlist: `*`, then `!pyproject.toml`, `!uv.lock`, `!src/`
  and whatever else the package build needs.
- No secret as a build argument (provenance records them); a BuildKit secret mount if
  one is ever needed.
- Both bases pinned by digest, with the tag in a comment.
- A fixed numeric UID for the runtime user.
- OCI labels `org.opencontainers.image.source`, `.revision` (build arg) and
  `.version`.

Acceptance criteria:
- [ ] `docker build` fails when `uv.lock` is out of date with `pyproject.toml`
      (shown in the PR, before and after).
- [ ] A layout test (run in CI by draft 7, skipped without Docker locally) builds the
      image and asserts: no `/app/tests`, `/app/evals`, `/app/.git` or source tree; no
      `.env*`, `*.pem` or `*.key` anywhere under `/app`; `import neuron_agent` works;
      the system prompt loads through `prompts/loader.py`; the user is a numeric
      non-root UID; the `CMD` and `HEALTHCHECK` are exactly the expected ones.
- [ ] `/health/live` answers from a container started with test settings (checked
      from inside the container).
- [ ] `OPERATIONS.md` "Deployment" describes the image (what is in it, how to build
      it).
- [ ] `make format lint typecheck test security` pass.

## 3. Server entrypoint: Uvicorn configured from `Settings`, no public bind by default

**Labels:** `deployment`, `security`, `reliability`, `priority:p0`, `v0.6.0` · **Depends on:** 2

`Dockerfile:18` runs `uvicorn ... --host 0.0.0.0 --port 8000` with no graceful-shutdown
timeout, while `OPERATIONS.md:468` and ADR 0004 tell operators to set
`--forwarded-allow-ips`. `api/main.py:600-601` reads `HOST`/`PORT` with `os.getenv`,
and `observability/telemetry.py:185` writes `OTEL_SEMCONV_STABILITY_OPT_IN`, both
outside `config/` and outside AGENTS.md's one exception. `APP_ENV` defaults to
`development` (`config/settings.py:37`) and `APP_AUTH_MODE` to `none` (`:94`), so an
image started on a platform without `APP_ENV` serves unauthenticated on `0.0.0.0`.
The app also parses `X-Forwarded-For` itself (`api/main.py:283`, `_client_ip`), so
there are two places that decide which proxy to trust. Blocked by ADR 0008 open
question 5.

Scope (ADR 0008 decision 3):
- `APP_HOST` and `APP_PORT` settings (`APP_PORT` also accepts `PORT`, which Render
  sets), in `.env.example`. The image sets `ENV APP_HOST=0.0.0.0 APP_PORT=8000`, and
  its `HEALTHCHECK` uses the configured port.
- `main()` passes host, port, `timeout_graceful_shutdown = APP_RUN_TIMEOUT_SECONDS +
  10`, one process, and the proxy-header choice from open question 5 (proposed:
  Uvicorn's proxy-header rewriting off, `_client_ip` the only parser, rightmost
  untrusted hop).
- `main()` refuses a non-loopback `APP_HOST` unless `APP_ENV` was set explicitly
  (`model_fields_set`); `docker-compose.yml` sets `APP_ENV=development`.
- `observability/telemetry.py:185` becomes AGENTS.md's second documented exception.
- The image's `CMD` becomes `["neuron-api"]`.

Acceptance criteria:
- [ ] No `os.getenv`/`os.environ` read or write remains outside `config/settings.py`
      and the two documented exceptions (`observability/langsmith_governance.py`,
      `observability/telemetry.py`); a test greps `src/` and fails on today's
      `api/main.py:600-601`. AGENTS.md lists both exceptions.
- [ ] A unit test asserts the Uvicorn config built by `main()`: host, port, graceful
      timeout derived from `APP_RUN_TIMEOUT_SECONDS`, `workers` unset, and the chosen
      proxy-header setting.
- [ ] Test: `main()` with a non-loopback host and no explicit `APP_ENV` exits non-zero
      before binding; the image started without `APP_ENV` exits non-zero (layout test,
      draft 2's harness); `make api` (loopback) and Compose (explicit `APP_ENV`) still
      start.
- [ ] With the chosen proxy handling, a request through a trusted proxy is keyed by
      the forwarded client address and one through an untrusted peer by the peer
      (existing `_client_ip` tests still pass, plus one through the real Uvicorn
      config).
- [ ] Negative test: a forged `X-Forwarded-For` from an untrusted peer appears in no
      log line or span attribute (captured logs and an in-memory span exporter).
- [ ] ADR 0004 "v0.4.0 Resource Limits" and `OPERATIONS.md:468` describe the single
      place proxy headers are parsed.
- [ ] `make api` and `make run` behave as before.

## 4. Graceful shutdown for `invoke`: readiness turns 503 and runs drain

**Labels:** `reliability`, `streaming`, `priority:p0`, `v0.6.0` · **Depends on:** 3

Streams already end with `service_shutting_down` within 2 s
(`api/main.py:102`, `_STREAM_SHUTDOWN_GRACE_SECONDS`). `/v1/agent/invoke` runs get no
shutdown signal and are bounded only by `APP_RUN_TIMEOUT_SECONDS=120`, and
`/health/ready` (`api/main.py:357-361`) keeps answering `200` while the process
drains, so a platform can keep routing to an instance that is stopping.

Scope (ADR 0008 decision 4):
- `AgentService` gains a draining flag (`begin_drain()`); `AgentService.prepare`
  (`services/agent_service.py:162`) raises a shutdown error while it is set, after a
  short drain delay; `api/` maps it to `503 service_shutting_down` with `Retry-After`.
- `neuron-api` runs a `uvicorn.Server` subclass whose `handle_exit` calls
  `begin_drain()` before Uvicorn's own handling, so readiness flips before Uvicorn
  stops accepting connections.
- Order on SIGTERM: `/health/ready` returns `503` at once; new runs are accepted for
  the drain delay, then refused; in-flight runs continue up to the graceful timeout;
  before exit, pending budget charges are flushed and leases deleted (best effort;
  expiry covers a SIGKILL).
- Logged once: `service_draining` with the number of in-flight runs.

Acceptance criteria:
- [ ] Unit test (calls `handle_exit(signal.SIGTERM, None)` on the server `main()`
      builds, app served in process): with a run in flight, `/health/ready` returns
      `503` at once; a new invoke after the drain delay gets `503
      service_shutting_down`; the in-flight invoke returns its `200` answer (fake model
      with a delay). It fails on `main` today.
- [ ] Subprocess test: real `neuron-api`, real SIGTERM, a stream in flight and an
      invoke in flight; the stream ends with `service_shutting_down`, the invoke
      completes, the process exits zero.
- [ ] Test: a run still in flight when the graceful timeout ends is cancelled,
      charges its partial usage and releases its lease (no leaked `thread_busy` or
      per-user slot).
- [ ] Stream shutdown behaviour is unchanged (existing tests pass).
- [ ] `OPERATIONS.md` documents the shutdown sequence and that the platform grace
      must exceed `APP_RUN_TIMEOUT_SECONDS + 10` plus the drain delay (Render
      `maxShutdownDelaySeconds: 150`; the blueprint test in draft 14 enforces it, since
      the app cannot read the platform value).

## 5. Enforce the request-body limit on chunked bodies

**Labels:** `security`, `reliability`, `priority:p1`, `v0.6.0` · **Depends on:** none

`limit_request_body_size` (`api/main.py:126-139`) checks only the `Content-Length`
header. A request sent with `Transfer-Encoding: chunked` has none, so its body is read
in full regardless of `APP_MAX_REQUEST_BODY_BYTES`.

Scope (ADR 0008 decision 5):
- Wrap the ASGI `receive` channel and stop reading at `APP_MAX_REQUEST_BODY_BYTES + 1`
  bytes, before any parsing or buffering, on every `/v1` route and before
  authentication.

Acceptance criteria:
- [ ] A chunked request whose body exceeds `APP_MAX_REQUEST_BODY_BYTES` gets `413
      payload_too_large` and logs `agent_request_body_too_large` without the body
      (test fails before the change); no more than limit + one chunk is read.
- [ ] A chunked request within the limit, and requests with `Content-Length`, behave
      as before; a declared length that understates the real body is also cut off at
      the limit.
- [ ] Tests: `Expect: 100-continue` with an oversized declared length is refused
      without reading the body; a slow-drip body crossing the limit is cut off when it
      crosses, not at its end; an unauthenticated oversized request gets `413`, not
      `401`.
- [ ] Streaming responses are unaffected (only the request body is counted).
- [ ] `OPERATIONS.md` "Common Failures" row for `413` says the limit applies with or
      without `Content-Length`, that Uvicorn serves HTTP/1.1 only, and that a
      proxy-level limit is defence in depth where the platform offers one.

## 6a. Production settings validation: refuse the remaining unsafe configurations

**Labels:** `security`, `deployment`, `priority:p0`, `v0.6.0` · **Depends on:** 10, 11b, 12, 13

`config/settings.py:150-257` refuses `AUTH_MODE=none`, the memory checkpointer, HTTP
JWKS URLs, a short identity key and CORS `*` in staging and production, but:
`APP_CHECKPOINTER=auto` silently becomes `none` (`config/settings.py:182`);
`APP_ALLOWED_HOSTS` defaults to any host (`:116`); `APP_TRUSTED_PROXIES` is unchecked
and defaults to an empty list (`:51`), so unset and explicitly empty look the same;
`APP_RATE_LIMIT_ENABLED` can be `false` (`:47`); `APP_CHECKPOINTER_SETUP_ON_STARTUP`
is allowed with replicas (`:80`); the Postgres DSN may omit TLS; API docs
(`:114`), `APP_AUTH_REQUIRE_TYP` (`:107`) and `APP_LANGSMITH_CONTENT_APPROVED` (`:54`)
are unchecked. Blocked by ADR 0008 open questions 5 and 6. Lands last among code
changes because it breaks existing configuration (ADR 0008 rollout).

Acceptance criteria (each a test that fails before the change, per environment;
ADR 0008 decision 9):
- [ ] Staging and production refuse `APP_CHECKPOINTER=auto` and
      `APP_LIMITS_BACKEND=auto` (both must be explicit); `APP_CHECKPOINTER=none` is
      logged at warning level; production refuses `APP_LIMITS_BACKEND=memory`.
- [ ] They refuse an empty `APP_ALLOWED_HOSTS`.
- [ ] They refuse an unset `APP_TRUSTED_PROXIES` but accept an explicit `[]`
      (`model_fields_set`, tested both ways), and refuse any catch-all range
      (`0.0.0.0/0`, `::/0`).
- [ ] They refuse `APP_RATE_LIMIT_ENABLED=false` and
      `APP_CHECKPOINTER_SETUP_ON_STARTUP=true`.
- [ ] They refuse a Postgres DSN (runtime or migration), parsed with psycopg's
      `conninfo_to_dict`, whose `sslmode` is below what open question 6 decides
      (default `verify-full`); a DSN with `sslmode` in a non-obvious place (URI query,
      keyword form) is parsed correctly; the error never prints the DSN.
- [ ] Production refuses `APP_EXPOSE_API_DOCS=true`; staging and production refuse a
      JWKS URL whose host is loopback, link-local or private.
- [ ] Production refuses `APP_AUTH_REQUIRE_TYP=false` if open question 2 says the IdP
      issues `at+jwt`; production refuses `APP_HSTS_MAX_AGE_SECONDS=0` once open
      question 13 says so.
- [ ] Production refuses `APP_LANGSMITH_CONTENT_APPROVED=true` without an
      acknowledgement setting naming the approval record.
- [ ] The effective limit values (rate, burst, concurrency, budget, timeouts, limits
      backend) are logged once at start-up (test on the log line).
- [ ] ADR 0005 decision 1 says `auto` is refused in staging and production.
- [ ] Development and test behaviour is unchanged; `.env.example` and
      `OPERATIONS.md` "Production Configuration Expectations" list the new rules;

## 6b. Database start-up checks: role, TLS and identity key

**Labels:** `security`, `state`, `priority:p0`, `v0.6.0` · **Depends on:** 6a, 10a

Nothing checks, at start-up, that the runtime database role is not the schema owner,
that the connection actually uses TLS, or that every replica has the same
`APP_IDENTITY_HASH_KEY` (`OPERATIONS.md:58-60`); a replica with a different key
silently orphans threads and splits limits. Blocked by ADR 0008 open questions 6 and
20.

Scope (ADR 0008 decisions 15 and 16):
- In staging and production, after the pool opens: refuse readiness if the runtime
  role is a superuser or has `CREATE` on the database or schema, if the runtime and
  migration DSN usernames are equal, if `pg_stat_ssl` shows no TLS for the process's
  own connection, or if the identity-key check value in `neuron_meta` (written by
  draft 10a) differs from this process's.

Acceptance criteria:
- [ ] Postgres tests: each of the four conditions keeps `/health/ready` at `503` and
      logs one stable error code without the DSN, password or key; the happy path is
      ready.
- [ ] The same checks run for the cron job's DSN (the prune CLI exits non-zero).
- [ ] Development and test skip them (no Postgres needed for `make test`).
- [ ] `OPERATIONS.md` "Thread Persistence" documents the checks and their error codes.

## 10. Versioned schema migrations as a deploy step

**Labels:** `state`, `deployment`, `reliability`, `priority:p0`, `v0.6.0` · **Depends on:** 1, 9

Schema setup is LangGraph's `setup()` plus `neuron_checkpoints_owner_idx`
(`persistence/checkpointer.py:39`, `CREATE INDEX CONCURRENTLY IF NOT EXISTS`), run by
`make db-setup` or at start-up. There is no record of neuron's own schema versions,
nothing stops two `setup` runs from racing, and a failed concurrent build leaves an
`INVALID` index that `IF NOT EXISTS` then skips silently. The runtime image has no
`make`. Blocked by ADR 0008 open questions 6 and 19.

Scope (ADR 0008 decision 7):
- `persistence/migrations.py`: an ordered list of neuron migrations recorded in a
  `neuron_migrations` table, applied by `python -m neuron_agent.persistence.cli setup`
  after LangGraph's `setup()`; concurrent index statements run outside a transaction.

## 21a. Readiness during IdP and guard-store outages

**Labels:** `reliability`, `auth`, `priority:p1`, `v0.6.0` · **Depends on:** none

`/health/ready` already re-probes the JWKS after a failure, throttled
(`security/auth.py:162-169`, #98), so on Render the platform's health checks drive
recovery; but `SECURITY.md:117` still says it recovers only when a later request
obtains a key and doesn't probe. Whether an instance with cached keys that still
verify stays ready during an IdP outage is untested.

Scope (ADR 0008 decision 12):
- An instance with a usable cached key set stays ready during a JWKS outage, and
  becomes not ready only when it has no usable keys.

Acceptance criteria:
- [ ] Test: after a JWKS outage, repeated `/health/ready` calls alone (no `/v1`
      traffic) bring the instance back to ready once the JWKS answers.
- [ ] Test: with a valid cached key set and the JWKS down, the instance stays ready and
      still verifies tokens signed with a cached key.
- [ ] Test: with `APP_LIMITS_BACKEND=postgres` (after draft 11a), readiness is `503`
      while the guard store is unreachable.
- [ ] `SECURITY.md:117` and `OPERATIONS.md` describe the actual behaviour.
