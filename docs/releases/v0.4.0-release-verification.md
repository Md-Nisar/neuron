## Findings

### Fixed during this gate run

- **Agent Server runs took authorization from the client (critical, BFLA).** Found by the first `agent_server_check.py` run.
  - Since #58 the graph declared `context_schema=AuthorizationContext`. LangGraph therefore built each run's authorization from the run's `context`, which Agent Server takes from the client's request (or from `config.configurable`).
  - A run without `context` crashed (`AuthorizationContext.__init__() missing … 'permissions'`), so every Agent Server and Studio run failed.
  - A run with `context={"permissions": [...]}` got exactly those permissions, bypassing tool scope checks.
  - The #58 smoke had checked thread creation and cross-user denial, but never a successful run.
  - Fixed in `0e2ccbb`:
    - the graph no longer declares a context schema;
    - the node uses an `AuthorizationContext` object (only `AgentService` can pass one) or else the permissions and owner Agent Server records in reserved `configurable` keys, which clients can't set.
  - Five new tests fail without the fix; two more pin the real tool middleware and the Agent Server reserved keys. The live check now also sends forged `context` permissions. An independent security review of the fix (context, config, assistant context, `Command`, stateless runs, crons, the inner agent) found no remaining path.
- **Key-rotation documentation was wrong.** `OPERATIONS.md` said a newly published key "works at once".
  - The PyJWT 2.15 upgrade in #61 added a 30-second cooldown on forced JWKS refetches after any successful fetch.
  - Measured with default settings, the new key was accepted only 30.2 s after publication.
  - The docs now say so and tell operators to pre-publish keys at least a minute ahead.
- **Undocumented limits gap.** The Agent Server path doesn't apply the API's rate limits, run caps, token budgets or message input policy. This is now in `SECURITY.md` and the known issues.

## Known Limitations of This Gate Run

- **Development settings for the real-server runs.** The API ran with `APP_ENV=development` so the IdP double could serve its JWKS over plain HTTP. HTTPS enforcement outside development, and the startup refusal in staging and production, were verified separately.
- **No real IdP.** The tokens came from an in-process IdP double, not a hosted identity provider.
- **One process, one machine.** Per-process limits weren't exercised across replicas. The Agent Server check used `langgraph dev` (in-memory), not a LangSmith deployment.
- **Fake models only** (see Live Model Results).

## Remaining Risks

- **Per-process limits.** Rate limits, run caps and token budgets are in memory per worker, not shared across replicas, and reset on restart.
- **Agent Server deployments rely on the platform for resource limits.** Neuron's API-layer guards don't apply there.
- **No token revocation.** A stolen access token works until it expires, and streams check their token only at the start.
- **Key rotation.** An IdP that signs with a key the moment it publishes it causes up to 30 s of `401`s per process.
- **Readiness is passive.** After an IdP outage, an instance taken out of rotation recovers only when it serves a request.
- **One issuer per deployment.** The owner key isn't length-prefixed for multi-issuer use.
